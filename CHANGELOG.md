## [Unreleased]

### Added

- `review-code` now folds an eligible first-review context build into the pull-request root fetch. The root invocation in `references/pull-request-target.md` fetches the root page, then a guard written in standard-library Python reads that saved page and reports `eligible` only when the target is open and unmerged with its required root fields present and valid, the posting identity is known, no review, thread comment, or pull-request comment on the page is authored by that identity with a trailing `[bot]` ignored, the `reviews`, `reviewThreads`, and `comments` connections and every returned thread's `comments` connection each report `hasNextPage: false` with `totalCount` matching the nodes returned, and both pinned commits are present locally with a resolvable merge-base. Any other state prints `deferred: <reason>` at exit 0 and step 2 keeps its current first-review or re-review build, `--prior-head`, `--base-ref`, and the duplicate-review shortcut included; a missing commit or unresolved merge-base defers rather than fetching or failing, and a guard that exits non-zero without a verdict defers as `eligibility guard failed with exit <status>` with its stderr visible. On `eligible` the invocation runs the existing first-review build with the pinned SHAs into the step-2 store path and redirects its stdout to `<private-dir>/context-build.out`, so the compliance diff is persisted privately and read once after the ledger's rows exist, and a chunk the inventory marks `consumed` counts as read only when that file is. Step 2 reuses the early store exactly once and runs no second build; a supplied phase-1 packet replaces the fetch and runs neither the guard nor the build. A root-query failure and an early build failure each print their output and stop with the command's exit status. `audit-code-publish` builds its changed-file manifest immediately after the root query and before continuation pages, with the shared block, guidance closure, fingerprint, and duplicate gates unchanged and no finder dispatched earlier. `test_command_chains.py` runs the documented block against root fixtures for a proven first review, prior state from the identity with and without the `[bot]` suffix, a top-level continuation, a nested thread-comment continuation, missing pagination metadata, a merged target, missing base and head objects, an unresolved merge-base, a failed root query, and a failed build, and checks the early store byte for byte against a direct build; the proven-first-review, prior-review, failed-root-query, and failed-build cases run under every available shell, the other deferral cases under `sh`. On a proven first review the root fetch and the context build go from two invocations to one; no time, cost, or quality effect is claimed, and #265 owns that assessment. Workflow `v5b-21` and audit `v2b-7` are retained because admission, verification, rendering, and thread-state semantics are unchanged (issue #258).

Identity resolution changes no admission, verification, rendering, thread-write, or state semantics (issue #305).

- `implement-publish` now hands its step-4 reviewer an evidence packet and keeps it current through every continuation. The initial brief carries the step-3 checks as `review-code`'s caller-supplied check evidence, in the form the rubric's Supplied check evidence section requires — command or check-run identity and scope, the full head SHA, the input state and whether the tree was dirty, the exit status or conclusion and whether the check finished, the claimed coverage including anything skipped, the environment, and readable output or an immutable artifact location — together with the acceptance evidence step 3 now records for a spec criterion a check does not settle: the criterion, the tested head and input state, the runtime, host, or environment configuration, the method, the observed result, and its output or artifact location. That evidence is observations only; a conclusion that a criterion is satisfied, the reasoning behind a change, an argument for its correctness, and the implementation conversation all stay out, and no live-test requirement is invented where the spec has none. Every criterion whose required evidence is missing is named in the packet and stays the reviewer's to raise as a material question or coverage gap. After fixes the packet is updated before the continuation with new evidence for the work the fixes reached, each unaffected check and each unaffected piece of acceptance evidence retained under the head and input state it ran or was exercised at, and every invalidation decision with its reason; acceptance evidence the fixes reach is exercised again at the new head or recorded as that gap, the addendum checks those decisions against the complete fix delta itself rather than accepting them, and a retained result is never relabelled as a run or an exercise at the final head. Fixes sharing one meaningful check produce one execution and one continuation. The packet is written where a fresh continuation can read it and its path is kept with the review record's paths; packet evidence that is missing, unreadable, incomplete, or contradicting its own invalidation decisions is a reported coverage gap, never a clean addendum. Step 5's pull-request verification bullet now names each piece of acceptance evidence with its criterion and the head and input state it was exercised at, beside each check, so a criterion no check settles reaches the published pull request evidenced rather than as the next reviewer's question. Workflow `v5b-20` is retained: this is caller-side transport and changes neither review admission nor publication policy (issue #295).

- `resolve-review` now hands its step-3 reviewer the round's check evidence and says when that reviewer runs a check itself. The dispatch carries each check in the protocol's Reporting form — its command or check-run identity and scope, the full head SHA it ran at, its input state, its exit status or conclusion, its coverage, and whether it was a run or a reuse — and the retention list carries that evidence to every later phase, delta re-verifications included, together with the addresser's invalidation list and the reason each retained check's inputs, environment, and coverage are unaffected. Those lines are the whole hand-off; the implementation conversation still does not cross over. The reviewer determines which checks the changes under review require under Selecting and Invalidating before it reads the evidence, reuses what meets the Reusing conditions for an obligation that exists, and keeps that reuse apart from retained historical evidence: a check that passed at an earlier head whose inputs, environment, and covered behavior the delta does not affect stays attributed to that head, is never relabelled at the later head, and cannot satisfy an explicit requirement for that check there, while the differing SHA alone is no reason to run it again for unchanged work. It runs a focused check where evidence is missing or stale for an actual obligation, is narrower than the change's reach, or does not reach a suspected defect it is investigating; uncertain reach or a relevant input or environment change invalidates retained evidence, and broader verification follows the protocol's Invalidating rule and repository or caller policy. Its assessment names reused evidence, retained historical evidence at its original head, and the checks it ran with their reasons, or states that it ran none. No suite-run cap is introduced, and the phase structure, awaited routes, verdict semantics, and the protocol's Check evidence rules are unchanged. Workflow `v5b-20` is retained (issue #287).

- `review-code` now takes an optional caller-supplied check-evidence input and validates it before reusing it. The rubric's new Supplied check evidence section requires each item to identify the command or check-run identity and its scope, the full head SHA and the actual input state it ran against including whether the tree was dirty, the result and completion state, the claimed coverage with skipped tests and matrix legs, the relevant environment, and readable output or an immutable artifact reference; an item missing any of these is unavailable evidence. An item stands in for a check only when its identity, inputs, environment, completeness, and coverage all match the obligation, and a run on uncommitted work counts only for the commit made from exactly that tree. A new head is an invalidation boundary rather than an automatic rerun obligation: evidence the delta does not reach stays attributed to its original head as historical, is never relabelled at the new head, and cannot satisfy an obligation naming that head, while uncertain reach resolves against reuse. The reviewer selects its own check when relevant inputs changed, dependency reach is uncertain, supplied coverage is too narrow, an item is incomplete or unreadable, or a candidate still needs falsification the evidence does not reach. The record keeps accepted, historical, and reviewer-executed evidence distinct, and test failures, environment failures, unavailable checks, and accepted evidence stay separately identifiable on the `Coverage` line. Supplied evidence reaches a verifier only through the handoff's permitted `test_evidence` fields, without claimed coverage, caller conclusions, or implementation reasoning. Changed-test operational inspection, disposable execution, the time limits, the suite-once rule, the mandatory verification triggers, and the one-initial-plus-one-follow-up batch cap are unchanged, and supplied evidence never establishes a clean verdict. Workflow `v5b-19` advances to `v5b-20` because verification semantics change (issue #294).

Step 1 takes a UTC timestamp inside the invocation that already runs the collection block and appends it to a single `timeline` file in that block's directory, which every later step writes to as well, step 6's second collection included. Each timed shell operation, each check above all, is bracketed by paired `start` and `end` events inside its own existing invocation, with the operation's exit status and failure handling untouched; step boundaries are separate events, and a reused check result gets one unpaired `check-reuse` line with its head and check name rather than a timed run. No tool call exists only to read a clock. The round is measured from the opening read's host-reported dispatch time, or from the earliest recorded timestamp with the opening portion excluded by name, to a `verification-complete` event after step 6's reconciliation. Step 6's report to the caller gains a cost section: wall clock per step, the measurement endpoints, every unallocated or excluded interval, each check invocation with its duration and whether it ran or was reused, how many times each documented check ran, the reviewer's reported tokens, wall clock, and tool uses per phase, and the host's tool-call count and total wall clock where it reports them. Missing host figures stay `unavailable` rather than zero, nested check and reviewer durations break a step down instead of adding to it, and counts stay counts: a tool call is not a model request and no saving is claimed. The addressing summary comment, every forge write, and `finish-it` are unchanged, and the skill still ships no timing script. Workflow `v5b-19` is retained because nothing about admission, verification, rendering, or publication changes (issue #288).

Workflow `v5b-19` is retained because no admission, verification, rendering, or publication semantics change (issue #285).

The fallback to the authenticated user belongs to identity resolution before the review runs, not to a half-published review. The shared thread-write loop is untouched and both references keep the byte-identical copy the suite enforces, `finish-it` decides gating authorization in its first step and carries it in the handoff packet, so a subagent never infers it, and a review request is neither sent nor mentioned for an app reviewer, which GitHub cannot route and `@` cannot notify. Workflow `v5b-17` advances to `v5b-18` and audit `v2b-6` to `v2b-7` because prior-state matching is state semantics; one fresh review per open pull request at its next run is accepted (issue #277).

- `review-code` now records forge fetch, focused-test, and publication-write intervals at command boundaries. `scripts/run_events.py wrap --private-dir <dir> --event <name> [--data key=value ...] -- <command>` runs an existing command with its streams, environment, and exit status intact and appends one `forge-fetched`, `focused-test-ran`, or `forge-written` event. It exits 2 with one `run_events:` line only for its own argument or execution failure, and it forwards cancellation without ever reporting success after one. A pull-request review creates its private directory before the step-1 fetch and wraps the root, continuation, issue, and CI reads there. The primary wraps its focused tests, and `review-code-publish` wraps its head fetches, readbacks, and review, reply, and resolution writes. `summarize` reports each group's event count, failed attempts, and interval union without summing overlaps. Independent wrapped events may be appended out of order, but script order and write-after-payload order are still enforced. Publication completion, root dispatch, idle wait, usage, and cost stay unavailable. Workflow `v5b-17` is retained because review semantics and existing script outputs are unchanged (issue #254).

- `finish-it`, a user-invoked orchestrator that runs one delivery: a spec, issue, branch, or pull request goes through `implement-publish`, a `review-code-publish` review, and rounds of `resolve-review` plus re-review, each step in a fresh-context subagent with a fixed handoff packet. It locates its first step from forge state, counts completed rounds from addressing summaries, runs `max(1, N − D)` further rounds with N defaulting to 3, always runs the first round, and from the second stops early on `Approved` or no progress. A prose spec becomes an issue first. `CONTEXT.md` records the shared terms spec source, round, and delivery, and `AGENTS.md` names the skill's runtime dependencies as the second install-alone exception (issue #249).

- `review-code` now records ordinary-run timing at the scripts every run already calls. The context build, each verifier brief and accounting, and each stored composition append one event to `run-events.jsonl` in the private directory. Each event carries a monotonic clock domain, the workflow, the harness when an environment marker names it, batch mode and counts, and returned verdict counts. Recording is silent, and a failed append changes no output or exit status. `scripts/run_events.py summarize` separates captured intervals from proxy brackets and from fields no script can observe: root dispatch, inspection, focused tests, idle wait, publication, caller mode, and usage, which stays null rather than zero. It never sums overlapping spans as elapsed time, and it can emit the #130 timing sidecar. Workflow `v5b-17` is retained because review semantics and every script output are unchanged (issue #218).

- `review-code` local sessions now recheck fixes using persisted prior state and bounded deltas, carry user decisions while re-deriving amendments, and retain snapshots through owned refs cleaned up at exit. A moved real HEAD resets the review; an unchanged chained tree needs no new record. Verification budgets remain per run with one further authorized batch per session. Pull-request and one-shot behavior remain unchanged at workflow `v5b-17` (issue #228).

- `implement-publish` now sends its committed local base-to-head range through `review-code` in a resumable fresh-context general-purpose subagent before publication. Blocking fixes return to the same reviewer for bounded re-verification and complete fix-delta inspection, with a fresh one-shot review when the delta is too large; the reviewed source stays read-only and focused tests stay disposable. Workflow `v5b-17` is retained because the review core's admission, verification, rendering, and state semantics are unchanged (issue #234).

- `review-code` session mode now handles answers, challenges, risk acceptance, and bounded deeper checks after the validated review. It preserves the immutable review record beside a private decision layer and a separately validated session record; acceptance alone changes neither status. Workflow `v5b-17` is retained because the one-shot review and published behavior are unchanged (issue #233).

- `review-code` now reviews local ranges and working-tree snapshots, infers branch bases, and carries commit-message requirements through verification and rendering. Snapshots preserve the real index and working files, include non-ignored untracked files, and reset parent chaining when real HEAD moves. Local coordinates stay code spans; ordinary review requests select the core, while `code-review-publish` remains the posting entrypoint. Pull-request output and fixtures remain byte-identical, so workflow `v5b-17` is retained (issue #232).

- `references/review-protocol.md`, mirrored in `code-review-publish-legacy` and `code-review-address`: one comment shape for findings and replies, carrying a rendered-invisible trailer so a finding keeps a stable id across review rounds; a shared disposition vocabulary; and a `gh` verb reference covering batched review submission, inline replies, and GraphQL thread resolution and reopening.
- Questions as a first-class item on both sides. A reviewer that cannot judge code without knowing something raises a `[Question]` instead of guessing a finding; an addresser stuck on a finding replies `needs-info`. A whole-change question carries a stable id in the review body and closes when its answer entry and reply trailer appear in the round's addressing summary. Questions count toward no axis and toward no round cap; the same open question is not re-posted, and it holds `Needs Information` until answered or withdrawn rather than aging into approval.
- An `answered` disposition, which the prose already assumed and the vocabulary lacked.
- A two-round cap per finding. A finding declined once and then verified unfixed becomes disputed, and is listed for a human to settle instead of being re-posted, so a review loop cannot re-litigate one point forever.
- `implement-publish`, which implements the work described by a spec, issue, or set of tickets and opens one pull request for it, delegating implementation to the best matching installed skill.
- An addressing summary. `code-review-address` closes each round with one general pull-request comment — the head addressed, counts by disposition linked to their threads, whole-change answers with their reply trailers, what still needs someone, the checks run, and whether the round is finished or waiting — and requests a re-review from the identity whose review it addressed where the forge routes them. Resolving every thread had left the pull request looking untouched, since the forge collapses what is resolved: a round that answered everything and a round that did nothing rendered the same. One comment per round however large it was; only whole-change answers carry per-item detail there because they have no thread.
- A status on every completed review: `Changes Requested` while any blocking finding is unsettled, `Needs Information` only where a concrete unanswered question could change the verdict, and `Approved` otherwise. Each axis records Passed, Findings, or `Not applicable`, plus Waiting for information where needed; an operationally unassessed axis aborts publication instead of falling through to approval.
- The status rides the forge's review event where one can carry it, and is written on the summary's first line where none can — `Needs Information`, no review system, a self-authored pull request GitHub will only take a `COMMENT` on, or a reviewer unauthorized to gate a merge. A non-gating `Changes Requested` or `Approved` uses its defined advisory form. A status that moves without the head moving — a decline accepted, a question answered — is published as a new review, since a review's state is fixed at submission and GitHub's update endpoint rewrites only the body. A superseded `COMMENT` needs no dismissal; only a gating state the new event cannot replace does.
- A severity on every finding. Blocking is the default and goes unmarked, since that is what an author assumes a review comment means; only the exception is labelled `[Suggestion]`, in the title line and in the trailer as `severity=optional`. The status derives from it, an author can close an optional finding unactioned, and `code-review-address` reads it to know which findings must clear before the pull request can merge — treating anything unmarked, a human's comment included, as blocking.
- Review events carry the status only where the user or the repository's documented workflow authorizes the reviewer to gate a merge; otherwise the review is submitted as `COMMENT` with the status written in the body. Permission changes the transport, never an `Approved` conclusion into `Needs Information`.
- A scripts convention in `docs/agents/scripts.md`: skill scripts are standard-library Python 3.9+ on macOS and Linux, do mechanical work only, and are invoked as `python3 scripts/<name>.py` from `SKILL.md`. Skills that ship scripts declare the requirement in their `compatibility` frontmatter.

### Changed

- `review-code`'s runtime references no longer carry text the reviewer does not act on. `rendering.md` drops the rendered finding, question, observation, and summary templates and its three overlapping inventories of what `compose_review.py` and `validate_review.py` check and refuse; the composer's `--example` and its printed violations are the reference for both, and the reviewer-facing rules — authored `Source` coordinates, the `Intent`, `Issue fit`, and `Coverage` lines, section order, file-anchor `side` derivation from the pinned merge-base manifest, the store checks, and comment repair — stay. `verifier-handoff.md` replaces its field-by-field input schema with the builder's `--example` and keeps the `test_evidence` projection rule, the source and conformance inputs, and the compact ledger-row form. The rubric's Private finding record states the survivor's fields in one sentence instead of a YAML example; `re-review.md` states the six addresser dispositions and the reply trailer in one sentence and keeps the prior-item trailer the reviewer writes by hand. `review-record.md` loses its ownership pointers to `rendering.md` and `re-review.md` and its restatement of the implementation-gate record's contents; `SKILL.md` loses its ownership bullets, the store's flag-level recovery detail, and the step-5 restatement of what the composer validates, with both step-5 blocks byte-unchanged. `local-targets.md`'s snapshot mechanics and pruning note move into `review_context.py`'s docstring, and `pull-request-target.md` drops the `fullDatabaseId` and `lastEditedAt` notes that `forge_packet.py` and `re-review.md` already carry. The always-loaded set (`SKILL.md`, the rubric, the record, and `rendering.md`) goes from 105,209 to 92,664 bytes; `verifier-handoff.md`, `re-review.md`, `local-targets.md`, and `pull-request-target.md` lose a further 2,508. Every `test_*.py` suite and both self-tests pass. Workflow `v5b-22` is retained: no admission, verification, rendering, or state rule changes, and DESIGN.md's Rule ownership table remains the maintainers' map (user request, 2026-09-20).

- `review-code` now dispatches the no-material-survivor clean-verdict verifier batch only when the candidate ledger holds an attackable row: any kind but `maintainability` or `requirement`, any row a verifier refuted, or a row the reviewer marks `attackable` because its acquittal rests on a safety premise. A ledger of hygiene and requirement acquittals, or an empty one, records `clean_verdict: not-required` and runs no batch; the follow-up attack after refuting the last material finding is unchanged. `workflow` advances to `v5b-22`.
- `finish-it`, `implement-publish`, and `resolve-review` no longer carry a subagent tier rule of their own. `finish-it` fixed its step subagent tier at the session's own tier, so a top-tier orchestrator dispatched top-tier steps against the repository's subagent tier rule while those steps dropped their own reviewers a tier; `implement-publish` and `resolve-review` restated that repository rule for their reviewer and verifier dispatches, a copy that would win any later conflict with `AGENTS.md`. Each dispatch now takes the tier the caller names where the skill accepts one, otherwise the tier the repository's instructions or the harness default give, and states the tier it selected. `resolve-review`'s caller-named reviewer tier, its rule that a fresh continuation runs at the tier of the phase it replaces, `implement-publish`'s same-tier continuation, and `finish-it`'s nested `reviewer tier: <name>` pass-through are unchanged; no workflow identifier changes.

- `resolve-review` now reads `addressing-protocol.md`, and then the repository's `docs/agents/issue-tracker.md` when it is present, each completely and on its own with the tool that returns whole files, in place of the #256 rule that read the pair in one invocation when the output fit the host's limit. That pair is large where `review-code`'s grouped pairs are small, and on Claude Code the combined read overran the tool-output limit on PR #278 and cost three recovery reads. Where every available read is bounded, the opening reads in ranges and recovers any portion a read cut off, detected by the tool's truncation notice or a read that ends before the file's last line; no host tool, output limit, or file size is named. The protocol is still read first, step 1 still skips a tracker the opening loaded, and `review-code`'s grouped reads are unchanged. `resolve-review/SKILL.md` grows from 3,509 to 3,524 words. Workflow `v5b-21` is retained (issue #286).

- `resolve-review` now bounds every phase after the first assessment and draft check to the previous phase's findings, the complete fix delta, and the revised drafts. The previous assessment and evidence remain authoritative for unchanged parts of the round, while a delta too large to inspect still triggers a fresh full assessment. Starting with the first re-verification, only a blocking defect introduced by the fixes or an unsupported reply or disposition claim earns another commit and re-verification. - `code-review-publish-legacy` publishes a linked summary index in two phases, since a batched review creates its body and comments in one call and the comment URLs do not exist until it returns.
- `implement-publish` pushes the head branch before both the existing-pull-request and create paths. Pushing only on the create path left an existing pull request advertising a head without the new work.
- Both skills close threads, and the bar for closing widened past "its work is done" to cover threads gone obsolete, outdated, or irrelevant. A stale thread from an earlier round is the reviewer's to close.
- The pull request under review is a fixed target: neither review skill opens, retargets, or closes one. `code-review-publish-legacy` stops and reports when a change has no pull request, and `code-review-address` commits fixes to the pull request's existing head branch rather than branching away from it.
- `code-review-publish-legacy` takes its fixed point from the pull request's own merge-base with its base branch instead of asking for one, so a review can run unattended.
- A finding scoped to a whole file attaches to that file inside the review rather than falling out to a general pull-request comment.
- All three skills drop their capability-negotiation prose. Both review skills read their forge verbs from the shipped protocol reference; `implement-publish` needs only two commands and carries them inline. The freed budget went into the behaviour above rather than into a shorter file: `code-review-publish-legacy` is 1,184 words against 820, `code-review-address` 1,172 against 839, `implement-publish` 358 against 459, with the 4,141-word protocol reference loaded only when a review skill reaches for it.

### Removed

- `review-code`'s session layer. `references/session.md` is deleted, with the session record, its amendments, the side-by-side display, the one further verifier batch per session, the `refs/review-code/session/` snapshot ref chain, and the local session recheck that reviewed only the delta through `--worktree --parent`. Session mode still asks before falsification and presents the record and routed questions afterward; `SKILL.md`'s new Interactive use section says that an answer, a supplied input, a chosen reading, or changed code starts a fresh run with that answer as an up-front input, under its own batch cap, with the earlier record's path reported beside the new one, and that a fix request is outside the review. Every local run is a first review in its own `mktemp -d` directory, and `re-review.md` loads only for pull-request prior state. `review_context.py` keeps `--worktree --parent` and `--prior-head` and its ref-protection test. The one-shot column, every named stop, the batch cap, and the published record are unchanged; workflow `v5b-22` is retained. `session.md` 9,519 → 0, `re-review.md` 12,424 → 7,190, `local-targets.md` 8,288 → 6,707, `review-record.md` 14,813 → 14,320, `SKILL.md` 35,792 → 36,520 (user request, 2026-09-20).

- Reactions from the review protocol and both skills that used it. A reaction repeated what the reply's disposition and trailer already said, its main reader is an agent that reads the reply body rather than the reaction, and posting one cost a request per comment.

## [0.0.2] - 2026-08-29

### Changed

- `code-review-publish` publishes only to the pull request: one review summary comment plus one line comment per finding, submitted together as a single pull-request review. When the pull-request author and the reviewer are the same user, the summary is posted as a general pull-request comment.
- `code-review-publish` treats the originating issue as the spec source only and no longer records the review in the issue tracker.
- `code-review-publish` supports re-reviews: when an earlier review exists at a different head SHA, prior findings are reassessed as resolved, still present, obsolete, or superseded, follow-ups go to existing threads, and the summary records both head SHAs.

## [0.0.1] - 2026-08-28

### Added

- `code-review-publish`, which reviews an issue-linked pull request, publishes one pull-request comment per finding, and records the review in the issue tracker when supported.
- `code-review-address`, which evaluates every pull-request review comment, makes warranted changes, replies to every comment, and resolves or reacts to feedback when supported.
- Setup and installation through the `skills` CLI for Codex, Claude Code, Pi, and OpenCode, plus provenance-checked global synchronization from GitHub `main` with systemd and launchd timers.
