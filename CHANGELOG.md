# Changelog

## [Unreleased]

### Added

- Reviews can now publish as a GitHub App while the human keeps authoring, so a pull request whose author would otherwise be reviewing their own work can use GitHub's review system: an app review is not a self-review, and `APPROVE` and `REQUEST_CHANGES` are open to it. `docs/agents/issue-tracker.md` declares the reviewing app and its review-token command per repository, and `review-code-publish` resolves that identity before the review runs, falling back to the authenticated user when the runner is absent or cannot authenticate, so an unusable app costs no review. Prior-state detection now keys on the **reviewer identity** rather than on whoever writes everything else, and every login comparison ignores a trailing `[bot]`, which REST carries and GraphQL omits for the same app — without that, an app's own prior review is invisible and every re-review restarts as a first review. Each block that writes a review acquires that token and proves it against the repository before its first write, so a non-empty token the forge refuses stops the block with nothing written instead of failing every reply in it; `audit-code-publish` and the legacy `code-review-publish` acquire it the same way for their own review writes, while every addressing write stays the pull request author's. The shared thread-write loop is untouched and both references keep the byte-identical copy the suite enforces, `finish-it` decides gating authorization in its first step and carries it in the handoff packet, so a subagent never infers it, and a review request is neither sent nor mentioned for an app reviewer, which GitHub cannot route and `@` cannot notify. Workflow `v5b-17` advances to `v5b-18` and audit `v2b-6` to `v2b-7` because prior-state matching is state semantics; one fresh review per open pull request at its next run is accepted (issue #277).

- `review-code` now records forge fetch, focused-test, and publication-write intervals at command boundaries. `scripts/run_events.py wrap --private-dir <dir> --event <name> [--data key=value ...] -- <command>` runs an existing command with its streams, environment, and exit status intact and appends one `forge-fetched`, `focused-test-ran`, or `forge-written` event. It exits 2 with one `run_events:` line only for its own argument or execution failure, and it forwards cancellation without ever reporting success after one. A pull-request review creates its private directory before the step-1 fetch and wraps the root, continuation, issue, and CI reads there. The primary wraps its focused tests, and `review-code-publish` wraps its head fetches, readbacks, and review, reply, and resolution writes. `summarize` reports each group's event count, failed attempts, and interval union without summing overlaps. Independent wrapped events may be appended out of order, but script order and write-after-payload order are still enforced. Publication completion, root dispatch, idle wait, usage, and cost stay unavailable. Workflow `v5b-17` is retained because review semantics and existing script outputs are unchanged (issue #254).

- `finish-it`, a user-invoked orchestrator that runs one delivery: a spec, issue, branch, or pull request goes through `implement-publish`, a `review-code-publish` review, and rounds of `resolve-review` plus re-review, each step in a fresh-context subagent with a fixed handoff packet. It locates its first step from forge state, counts completed rounds from addressing summaries, runs `max(1, N − D)` further rounds with N defaulting to 3, always runs the first round, and from the second stops early on `Approved` or no progress. A prose spec becomes an issue first. `CONTEXT.md` records the shared terms spec source, round, and delivery, and `AGENTS.md` names the skill's runtime dependencies as the second install-alone exception (issue #249).

- `review-code` now records ordinary-run timing at the scripts every run already calls. The context build, each verifier brief and accounting, and each stored composition append one event to `run-events.jsonl` in the private directory. Each event carries a monotonic clock domain, the workflow, the harness when an environment marker names it, batch mode and counts, and returned verdict counts. Recording is silent, and a failed append changes no output or exit status. `scripts/run_events.py summarize` separates captured intervals from proxy brackets and from fields no script can observe: root dispatch, inspection, focused tests, idle wait, publication, caller mode, and usage, which stays null rather than zero. It never sums overlapping spans as elapsed time, and it can emit the #130 timing sidecar. Workflow `v5b-17` is retained because review semantics and every script output are unchanged (issue #218).

- `review-code` local sessions now recheck fixes using persisted prior state and bounded deltas, carry user decisions while re-deriving amendments, and retain snapshots through owned refs cleaned up at exit. A moved real HEAD resets the review; an unchanged chained tree needs no new record. Verification budgets remain per run with one further authorized batch per session. Pull-request and one-shot behavior remain unchanged at workflow `v5b-17` (issue #228).

- `implement-publish` now sends its committed local base-to-head range through `review-code` in a resumable fresh-context general-purpose subagent before publication. Blocking fixes return to the same reviewer for bounded re-verification and complete fix-delta inspection, with a fresh one-shot review when the delta is too large; the reviewed source stays read-only and focused tests stay disposable. Workflow `v5b-17` is retained because the review core's admission, verification, rendering, and state semantics are unchanged (issue #234).

- `review-code` session mode now handles answers, challenges, risk acceptance, and bounded deeper checks after the validated review. It preserves the immutable review record beside a private decision layer and a separately validated session record; acceptance alone changes neither status. Workflow `v5b-17` is retained because the one-shot review and published behavior are unchanged (issue #233).

- `review-code` now reviews local ranges and working-tree snapshots, infers branch bases, and carries commit-message requirements through verification and rendering. Snapshots preserve the real index and working files, include non-ignored untracked files, and reset parent chaining when real HEAD moves. Local coordinates stay code spans; ordinary review requests select the core, while `code-review-publish` remains the posting entrypoint. Pull-request output and fixtures remain byte-identical, so workflow `v5b-17` is retained (issue #232).

- `references/review-protocol.md`, mirrored in `code-review-publish-legacy` and `code-review-address`: one comment shape for findings and replies, carrying a rendered-invisible trailer so a finding keeps a stable id across review rounds; a shared disposition vocabulary; and a `gh` verb reference covering batched review submission, inline replies, and GraphQL thread resolution and reopening.
- Questions as a first-class item on both sides. A reviewer that cannot judge code without knowing something raises a `[Question]` instead of guessing a finding; an addresser stuck on a finding replies `needs-info`. A whole-change question carries a stable id in the review body and closes when its answer entry and reply trailer appear in the round's addressing summary. Questions count toward no axis and toward no round cap; the same open question is not re-posted, and it holds `Needs Information` until answered or withdrawn rather than aging into approval.
- An `answered` disposition, which the prose already assumed and the vocabulary lacked.
- A two-round cap per finding. A finding declined once and then verified unfixed becomes disputed, and is listed for a human to settle instead of being re-posted, so a review loop cannot re-litigate one point forever.
- `implement-publish`, which implements the work described by a spec, issue, or set of tickets and opens one pull request for it, delegating implementation to the best matching installed skill.
- An addressing summary. `code-review-address` closes each round with one general pull-request comment — the head addressed, counts by disposition linked to their threads, whole-change answers with their reply trailers, what still needs someone, the checks run, and whether the round is finished or waiting — and requests a re-review from the identity whose review it addressed where the forge routes them. Resolving every thread had left the pull request looking untouched, since the forge collapses what is resolved: a round that answered everything and a round that did nothing rendered the same. One comment per round however large it was; only whole-change answers carry per-item detail there because they have no thread.
- A status on every completed review: `Changes Requested` while any blocking finding is unsettled, `Needs Information` only where a concrete unanswered question could change the verdict, and `Approved` otherwise. Each axis records Passed, Findings, or `Not applicable`, plus Waiting for information where needed; an operationally unassessed axis aborts publication instead of falling through to approval.
- The status rides the forge's review event where one can carry it, and is written on the summary's first line where none can — `Needs Information`, no review system, a self-authored pull request GitHub will only take a `COMMENT` on, or a reviewer unauthorized to gate a merge. A non-gating `Changes Requested` or `Approved` uses its defined advisory form. A status that moves without the head moving — a decline accepted, a question answered — is published as a new review, since a review's state is fixed at submission and GitHub's update endpoint rewrites only the body. A superseded `COMMENT` needs no dismissal; only a gating state the new event cannot replace does.
- A severity on every finding. Blocking is the default and goes unmarked, since that is what an author assumes a review comment means; only the exception is labelled `[Suggestion]`, in the title line and in the trailer as `severity=optional`. The status derives from it, an author can close an optional finding unactioned, and `code-review-address` reads it to know which findings must clear before the pull request can merge — treating anything unmarked, a human's comment included, as blocking.
- Review events carry the status only where the user or the repository's documented workflow authorizes the reviewer to gate a merge; otherwise the review is submitted as `COMMENT` with the status written in the body. Permission changes the transport, never an `Approved` conclusion into `Needs Information`.
- A scripts convention in `docs/agents/scripts.md`: skill scripts are standard-library Python 3.9+ on macOS and Linux, do mechanical work only, and are invoked as `python3 scripts/<name>.py` from `SKILL.md`. Skills that ship scripts declare the requirement in their `compatibility` frontmatter.

### Changed

- `implement-publish` now defines which checks it runs, matching the Check evidence rules #263 gave `resolve-review`. Step 3 names what a check and its evidence are, defines the input state a result records, selects the repository's documented focused commands for the behavior the work changes and for what depends on it, treats a file-name match as a lead rather than a selection, runs a shared check once after the last change that shares it, adds the broader suite for shared dependencies or configuration, cross-module behavior, or uncertain reach, and reuses an earlier success only for the same check at the exact full head SHA with unchanged relevant inputs, environment, and required coverage; a run on uncommitted work counts only for the commit made from exactly that tree. Step 4 replaces "rerun affected checks" with the invalidation rule: rerun the focused checks covering the fixes' effects and the affected broader suite when they reach shared dependencies or configuration, cross modules, or have uncertain reach, however many suites already ran this step; a check the fixes do not reach needs no rerun. Every result establishes only the head and input state it ran at, the same exact-head principle as the existing rule that a further commit voids reviewer coverage, so the continuation and the publication gate read both the same way, and step 5's verification bullet now names each check with the head and input state it establishes and any remaining gap. - `resolve-review` now defines which checks a round runs and when earlier results still count. The addressing protocol's new Check evidence section has five rules. Selecting: fixes choose the repository's documented focused commands for the behavior they change and what depends on it. A file-to-test name match is a lead, a documentation-only change needs a test only when a documented check covers it, and changes sharing a check run it once. Reusing: a successful result stands in for a rerun only for the same check at the exact full head SHA, with unchanged relevant inputs and environment and the required coverage; an unchanged `HEAD` with dirty inputs is not enough. Invalidating: when internal-review findings cause further changes, the addresser lists the evidence they invalidate and reruns focused checks, adding the affected broader suite for shared dependencies or configuration, cross-module behavior, or uncertain reach, however many suites already ran. The internal reviewer and future CI do not substitute for it. CI: a new Reading check runs verb paginates `commits/<sha>/check-runs` for one full SHA. It writes `check-runs.<sha>.json` only on a complete read, retaining the requested and per-run head SHA, check id, name, app, check suite, Actions run id, status, conclusion, and evidence URL. A green unrelated job, incomplete matrix, skipped tests, another head or merge commit, and missing evidence establish nothing. Reporting: replies and the addressing summary name each check with the head and input state it establishes and any remaining gap, and the examples now qualify success by head. Steps 2, 3, 5, and 6 point at these rules, and the publication gate is unchanged. `code-review-publish`'s `review-protocol.md` takes the same reply, disposition-table, and summary wording under the shared-vocabulary rule, carrying the Reporting substance inline because that copy has no Check evidence section to cross-reference, and `README.md`'s account of the summary follows. `scripts/test_check_runs.py` in `review-code` runs the documented block against offline fixtures under `sh`, `bash`, `zsh`, and `dash`. `SKILL.md` grows from 2,131 to 2,205 words, and `addressing-protocol.md` from 6,347 to 7,554. - `review-code-publish` and `resolve-review` now post already-decided thread replies, resolutions, and reopenings through one documented write loop. The loop reads a once-written `writes.jsonl` with `id`, `comment_id`, `thread_id`, `body` or null, `action` (`resolve|reopen|none`), and an optional recorded `is_resolved`. - `code-review-inspect` composes its publication payload from authoritative fields. `scripts/compose_review.py` takes each finding's, question's, observation's, and prior item's semantic fields and authored prose plus the run identity and summary, renders finding and question markup, trailers, summary counts, indexes, commit-pinned coordinate fragments, and conditional sections once, refuses a contradiction or omitted judgment by name — a `blocking` that disagrees with `action`, a duplicate or re-posted stable id, a file anchor without provenance, a status that contradicts an unsettled must-fix item or incomplete coverage, a fourth observation — validates the result with `validate_review.py`, and prints the payload the existing `--emit-batch` projection consumes. Prior items are accounted for in the summary only; thread replies stay with `re-review.md` and never enter the batch of new comments. A file-anchored finding or question carries its complete prose and trailer in the body. Workflow `v5b-15` to `v5b-16` (issue #220).

- Split the routine reviewer into `code-review-inspect`, which returns a validated record and batch without forge writes, and a thin `code-review-publish` wrapper. Install both together. Record semantics, rendering, and publication have separate owners; workflow `v5b-15`, prior trailers, and stable finding ids are retained. Authorized gating emission validates status/event compatibility, removes the advisory suffix mechanically, and re-validates before emission (issue #226).

- `code-review-publish` and `code-audit-publish` carry deleted-file provenance from the pinned merge-base manifest through publication. Known deleted whole files link at merge-base; unknown file path/revision stays unlinked. Ordinary head links, whole-file body fallback and native review head identity are preserved. Routine workflow `v5b-14` to `v5b-15`; audit protocol `v2b-5` to `v2b-6` (issue #84).

- `code-review-publish` publishes a question only for a named unresolved decision or fact with a concrete effect on this merge — its correctness, an explicit acceptance criterion, a compatibility or release obligation, or the present merge decision — and records how the answer settles it; a supplied benchmark the reviewer has not repeated, or an unverified adjective, no longer produces a measurement request or `Needs Information` by itself. An explicit deferral stays visible in the private record, and a preview surface the record accepts for this merge is reopened only when the change crosses the deferred release boundary, contradicts a rule, or leaves a material decision unresolved. Priority follows demonstrated impact and reach, so a confirmed or externally visible low-impact defect stays a `P3` finding rather than becoming a `P1` or an observation. Workflow `v5b-13` to `v5b-14`.
- `code-audit-publish` collects complete paginated forge inputs and fingerprints reviewed intent, explicit PR lifecycle and applicable base guidance. Duplicate suppression requires matching full code/input identity and no later evidence; original publication content, including the final linked index, is fingerprinted independently of forge timestamp drift. Changed same-head requirements or replies receive a new assessment, and new eligible findings survive unchanged aggregate status while standing findings retain their threads. Review protocol `v2b-4` to `v2b-5`.
- `code-audit-publish` runs its verifier in a genuinely non-inheriting worker and accounts for every verdict. The verifier starts in a fresh context — `fork_turns=none` where the harness supports it — with the pinned run identity, the rule and spec pointers, and bounded inspection; where that isolation cannot be provided, verification is incomplete, every candidate is withheld, and nothing imitates independence in the orchestrator's own context. Candidates carry a risk kind, an impact, and the proposed change through to the verifier, ledger rows carry a kind and a per-run id distinct from the durable finding id, and the prompt builder writes an accounting packet that a new `account_verifier_return.py` checks the return against: exactly one verdict per candidate and one ruling per related acquittal, with a missing, duplicate, unexpected, or malformed record refused and repaired once in shape only. A verifier that returns nothing to a non-empty packet is a failure, not a clean review; finders that return no candidates take an explicit clean-review path instead. Old ten-field candidates and four-field ledger rows are refused by name rather than misread. Review protocol `v2b-3` to `v2b-4`.
- `code-audit-publish` routes every unsettled thing through one ladder: settle it from a reachable source, ask it only where an outcome-changing fact no available source can settle remains, otherwise record it. A claim the reviewer could have looked up no longer reaches the author as a question to finish the review, and an unresolved record — a middle verdict, an unread file, an open deferral — is never evidence the code is correct. A refutation names one of five evidence bases and cites it; an approval establishes only what it explicitly accepted, and a deferral stays open evidence that publishes as a question only where the answer decides what this merge releases or what consumers can already depend on, so a deliberate preview naming decision no longer holds a merge by itself. A proven defect stays a `consider` finding at low priority instead of sinking into an observation, and an observation states a consequence shown absent rather than one merely unproven. Review protocol `v2b-3`.
- `code-audit-publish` attributes a regression to the guarantee a change removed rather than to the lines it touched. Unchanged code is in scope when the diff removed or weakened a lock, ordering constraint, ownership rule, validated invariant, check, or bound it relied on, so a byte-identical path that was safe at the merge-base and is unsafe at the head is this change's defect, cited with both revisions, the consumer, and the trigger. A path already unsafe at the merge-base stays pre-existing, and a refactor that preserves the guarantee introduces nothing. The verifier's `pre-existing` refutation has to compare the same path, trigger, and governing guarantee at base and head, and rules `plausible` where it cannot reconstruct the base state. Such a finding takes its fix site from the repair it proposes — the changed line when the protection should be restored there, the untouched consumer when the removal is deliberate and the consumer must adapt — and the existing anchor ladder runs from that, never by giving the consumer a fabricated diff coordinate. The Requirements-candidate exception and the paired old/new documentation sweep keep their own rules. Review protocol `v2b-1` to `v2b-2`.
- Rename `code-review-deep-publish` to `code-audit-publish` for the independent audit direction. Keep explicit-only invocation and the existing `v2b-1` review protocol; requirements/contract investigation is the current foundation, with stronger guarantee audits and verification tracked as future work. Historical run identities remain unchanged.
- `implement-publish` accounts for every issue provided or inferred, not just a spec link: the pull-request body names each with a disposition — closes it via the forge's closing keyword, partially implements it with what remains open, or affects it with how — so a reader sees the pull request's effect on each ticket.
- The v5a calibrated hybrid replaces the v5 workflow as `code-review-publish`, model-invocable like the rest of the loop: one integrated reviewer inspects the complete merge-base diff against a private rubric, `must-fix` and high-consequence findings are verified in a fresh context before publication, questions and observations are separate channels, and a mechanical validator gates every write. The former two-axis reviewer remains as `code-review-publish-legacy`, which is not model-invocable and is kept for historical purposes; invoke it explicitly only when the legacy two-axis protocol is specifically wanted.
- The round-closing re-review ask no longer depends on the forge accepting a review request. Where the forge routes none, or refuses this one because the reviewing identity authored the pull request, the addressing summary carries `Re-requesting review from @<login>.` instead — the mention notifies them, which is what the request was for. `code-review-address` settles which form applies before writing the summary and no longer explains the forge's refusal on the pull request, where a paragraph about a rejected API call was noise around the ask itself.
- `code-review-address` reconciles the pull request title and description with the final diff and originating spec before closing an addressing round, updating stale metadata while preserving still-valid context and issue links.
- Review findings use `[Code]` for correctness and implementation quality and `[Requirements]` for fidelity to the originating spec. New stable ids use `code/` and `requirements/`; legacy `standards/` and `spec/` ids keep their original values across re-reviews.
- `code-review-address` is model-invocable, so a review loop can reach it as its fix step.
- `code-review-publish-legacy` publishes through the forge's review system when it has one, submitting the summary as the review body with every finding batched as a line comment on the code it names. A general pull-request comment is now the fallback for a forge with no review system or one that refuses the review, not the default for a self-authored pull request.
- `code-review-publish-legacy` submits every line comment in one batched review rather than one review per finding, and its summary indexes findings instead of restating them.
- `code-review-address` resolves each thread as it finishes it rather than batching resolutions, and either skill can reopen a thread resolved too early.
- Review verdicts are `fixed`, `accepted`, `obsolete`, and `not-fixed`. `confirmed` was ambiguous — it could be read as the finding being confirmed still present, which is what `not-fixed` names — and there was no verdict for accepting a decline, so a reasoned refusal had nowhere to land.
- A `declined` reply no longer resolves its own thread. Declining states a position; the reviewer's `accepted` verdict settles it, so a live disagreement stays visible to the round cap instead of being closed by the party that lost it.
- `code-review-publish-legacy` publishes a linked summary index in two phases, since a batched review creates its body and comments in one call and the comment URLs do not exist until it returns.
- `implement-publish` pushes the head branch before both the existing-pull-request and create paths. Pushing only on the create path left an existing pull request advertising a head without the new work.
- Both skills close threads, and the bar for closing widened past "its work is done" to cover threads gone obsolete, outdated, or irrelevant. A stale thread from an earlier round is the reviewer's to close.
- The pull request under review is a fixed target: neither review skill opens, retargets, or closes one. `code-review-publish-legacy` stops and reports when a change has no pull request, and `code-review-address` commits fixes to the pull request's existing head branch rather than branching away from it.
- `code-review-publish-legacy` takes its fixed point from the pull request's own merge-base with its base branch instead of asking for one, so a review can run unattended.
- A finding scoped to a whole file attaches to that file inside the review rather than falling out to a general pull-request comment.
- All three skills drop their capability-negotiation prose. Both review skills read their forge verbs from the shipped protocol reference; `implement-publish` needs only two commands and carries them inline. The freed budget went into the behaviour above rather than into a shorter file: `code-review-publish-legacy` is 1,184 words against 820, `code-review-address` 1,172 against 839, `implement-publish` 358 against 459, with the 4,141-word protocol reference loaded only when a review skill reaches for it.

### Removed

- Reactions from the review protocol and both skills that used it. A reaction repeated what the reply's disposition and trailer already said, its main reader is an agent that reads the reply body rather than the reaction, and posting one cost a request per comment.

## [0.0.2] - 2026-08-29

### Changed

- `code-review-publish` publishes only to the pull request: one review summary comment plus one line comment per finding, submitted together as a single pull-request review. When the pull-request author and the reviewer are the same user, the summary is posted as a general pull-request comment.
- `code-review-publish` treats the originating issue as the spec source only and no longer records the review in the issue tracker.
- `code-review-publish` supports re-reviews: when an earlier review exists at a different head SHA, prior findings are reassessed as resolved, still present, obsolete, or superseded, follow-ups go to existing threads, and the summary records both head SHAs.

## [0.0.1] - 2026-08-28

### Added

- `code-review-publish`, which reviews an issue-linked pull request, publishes one pull-request comment per finding, and records the review in the issue tracker when supported.
- `code-review-address`, which evaluates every pull-request review comment, makes warranted changes, replies to every comment, and resolves or reacts to feedback when supported.
- Setup and installation through the `skills` CLI for Codex, Claude Code, Pi, and OpenCode, plus provenance-checked global synchronization from GitHub `main` with systemd and launchd timers.
