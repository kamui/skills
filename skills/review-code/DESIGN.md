# Review-code design

`review-code` inspects a pull request, committed range, or working tree and returns a validated review record. It does not publish. This file explains the current design for maintainers; [`SKILL.md`](SKILL.md) and its references define runtime behavior. The [design history](HISTORY.md) retains earlier rules, experiments, issue evidence, and release notes. Historical rules there may have been superseded.

## Review and verification

One reviewer reads the pinned change, checks its stated requirements, follows named risks into relevant unchanged code, and falsifies candidates before retaining them. This keeps the usual review in one context while giving requirement omissions and risks outside changed lines a path into the review. The reviewer accounts for every changed file, risk check, and required input before deriving coverage.

Independent verification is a separate, fresh-context step. A surviving candidate under a mandatory trigger becomes a required candidate task and needs a `confirmed` ruling to publish as a finding. When a review would have no blocker but the change touches a named safety area, the reviewer sends the concrete premises behind that conclusion as safety-premise tasks. The initial and follow-up batches share one allowance across the review and its continuations. The [verification-task change](HISTORY.md#verification-tasks-and-version-2-private-records-issue-331) explains why the former complete-ledger clean-verdict attack was retired. A low-risk clean review can finish without an independent verifier; its missed-defect risk remains open for the [bounded comparison](../../docs/research/review-code-rewrite-2026-09-22/README.md).

The reviewer judges evidence, admission, priority, and whether a safety area applies. Scripts build pinned context, package and account for verifier tasks, and reject contradictory records. Composition renders syntax and links from authoritative fields, so the reviewer does not assemble publication artifacts by hand. `review-code-publish` owns forge writes and their authorization.

## Concise runtime strategy, issue #332, 2026-09-22

Workflow `v5b-24` removes mandatory reading/search recipes and replaces the runtime manual with the strategy draft, selective procedures, and composer examples. It supersedes the historical inspection recipes and 73 KB budget; #331's verification policy and version-2 state remain. The always-loaded ceiling is now 26 KB, with separate limits for runtime total, expanded primary paths, and generated verifier briefs. [The runtime report](../../docs/research/review-code-rewrite-2026-09-22/runtime-layout.md) records the layout, justified entrypoint exception, baseline comparison, and limits. Word counts make no quality, latency, or cost claim; #333 owns the bounded comparison.

## Artifact-savings baseline, issue #341, 2026-09-22

The artifact-savings work (#340) optimizes mechanical authoring and helper discovery, not reference counts. Its [baseline](../../docs/research/review-code-artifact-savings-2026-09-22/README.md) maps each repeated field to the packet, store, input, chain file or judgment that owns it. It also archives four reconstructable interface tasks with a seeded version-2 continuation chain and freezes the paired Sonnet 5 High protocol. Feature changes must keep a mechanical field's authority and its existing check, and must leave judgments with the model. Workflow `v5b-24` and every private schema are unchanged.

## Generated reports and artifact returns, issue #342, 2026-09-23

The finalizer now writes `report.md`, so the model no longer writes the complete review a second time after validation. The report is the payload's summary body, the run identity the trailer does not carry, the full body of each line comment the summary only indexes, the private ledgers, routed state, and drafted prior-item replies. Every body appears once. Public payload, batch and fragment bytes are unchanged.

**Stronger precondition.** Finalization requires the composition's `record` for both profiles, with every section written explicitly and nothing defaulted. The composer still accepts a publishable composition without one, as earlier callers used it, but that alone cannot finalize. A publishable record requires `skill_root` in place of `addenda`. Prior items may carry `reply`, `thread_id` and `comment_id`, checked against the read-only `--packet`. The finalizer appends the prior-item trailer, and those fields never reach the payload. `--packet` is the argument #343 reuses for identity derivation.

**Returns.** `return_format: artifacts` lets skill callers take the finalizer's `--compact` status and paths and read the files themselves. `complete`, the default, still returns the whole review, and session and retrospective non-publishing output stay complete. Default finalizer stdout is unchanged.

**Success marker and state.** Outputs are staged, and `report.md` is promoted last. A new gate record, and the publishable composition kept in the private directory, carry `finalization` with protocol `review-code-finalization/1`, the profile, the absolute report path, and the rendered replies. A consumer, including the composer reading a carried chain file, accepts new-protocol output only when that report exists, and it refuses an unknown protocol. A record without `finalization` predates this change and keeps its existing validation. `implementation-gate-record/2` keeps its version: `finalization` is an additive key, and the protocol string is the discriminator. A rerun is refused before anything is modified while an addenda directory holds an addendum, or while an existing record cannot be read to name its addenda directory. An empty addenda directory is not an active chain. A private directory has one writer at a time: a retry or continuation starts only after the earlier process exits. Overlapping writers are unsupported, and the marker does not detect them.

**Workflow.** `v5b-24` is retained. Admission, verification, public rendering, and decision and state semantics are unchanged. The trailer text and its placement are the same; only who appends it changed. The [demonstration](../../docs/research/review-code-report-generation-2026-09-23/README.md) replays the finalizer on #341's archived cells: 9,351–10,054 hand-written report characters become a generated report, with no extra authored field. The PR primary load grows 2,853 bytes to 66,905 of 67,000, mostly because the publishable `--example` now shows the accounting it requires. No limit rises.

## Derived finalization metadata, issue #343, 2026-09-23

The finalizer's new first stage, `derive`, fills the mechanical fields a saved input already owns, so the model no longer copies them into `composition.json`. The store owns `head`, `merge_base`, and a working tree's kind and tree. The packet owns the pull-request kind, base ref and SHA, `merged`, the repository URL and issues, and its pinned head must be the store's. The saved fingerprint input (`--fingerprint-input`) owns a range's target, a local target's commit messages byte for byte, spec identities, issues without a packet, and the `context` digest. That digest is computed with `context_fingerprint.py`'s own normalization, guidance derivation and hash, never a second hasher. The finalizer run owns the record's `private_dir`, `store`, `composition`, `skill_root` and, for the gate, `addenda`. Each batch's bundle manifest owns its name and phase, and its accounting report owns the raw return, provided the report's manifest hash matches that bundle. An omitted field is filled. An explicit copy must equal its owner's value, so a digest computed early for the duplicate-review shortcut fails if the saved inputs changed. An omitted field no input establishes is named. Coverage, status, requirement dispositions, file states, task selection and rulings are never derived.

**Stronger precondition.** Copies that went unchecked before (base, repository URL, issues, `merged`, record paths, batch fields, and the digest whenever the fingerprint input is supplied) are now refused on conflict. A gate record can no longer name an addenda directory other than its own. The finalizer now runs in the reviewed repository, because deriving guidance reads its base. Without `--fingerprint-input` an explicit `context` is still accepted unverified, so older callers keep working. `compose_review.py --example` now prints only what the reviewer writes, including a prior item with its reply for the pull-request branch; the composer run alone refuses that input.

**Schemas and workflow.** `implementation-gate-record/2` and `review-code-finalization/1` are retained. Records keep their shapes; a gate record now always names `skill_root`, and `finalization.inputs` additively records the store, packet and fingerprint input paths that reproduce the digest. Derived keys take their customary order, so a derived record serializes exactly like a transcribed one. `v5b-24` is retained: the digest is the same function over the same inputs, and public rendering, admission, verification and state semantics are unchanged, so no duplicate-review shortcut is invalidated. The [demonstration](../../docs/research/review-code-metadata-derivation-2026-09-23/README.md) replays #341's cells with 16 and 13 fewer mechanical leaves and byte-identical public output. The always-loaded path grows 172 bytes to 25,953 of 26,000, while the PR and local primary paths shrink by 242 and 679 bytes. No limit rises.

## Worker-saved verifier returns, issue #344, 2026-09-23

The primary chooses a return transport before building a batch. With `--return-file`, the builder binds a fresh path outside the bundle, canonicalized through its parent's real path, as the manifest's `return_file`, and embeds the file-transport section of `verifier-return.md` with that assignment. The worker saves its existing JSON encoding there by exclusive create and replies with only the path and `complete`. The primary passes that path to the accounting helper unread, so the return no longer enters its context as a tool result, is not rewritten to `raw-return.json`, and is read once, inside `accounting.json`. Without the option, the brief keeps the inline transport and the primary saves the response once, as before. That is the path for hosts that cannot grant the worker one scoped write or cannot share the file with the primary.

**Accounting.** The helper requires the returned path to equal the assignment exactly and reads the file without following a link, from a parent that still resolves to itself. A wrong path, an absent, linked, non-regular or unreadable file, a moved parent, or a partial write withholds every task, as an unparseable return already did. A worker that wrote where the primary cannot read therefore produces an absent file and a withheld batch, not a phantom completion. `--inline-fallback` accounts the primary's verbatim save of an inline response after a failed write, recording the size and hash of anything left at the assignment. `--repair-of` records the original's path and hash beside a repaired return. Originals are never modified. Structural success is still only structural: confirmation, scope and coverage stay the primary's judgments, and neither transport nor encoding repair grants a batch.

**Instruction ownership.** `verifier-return.md` is now worker-only. The builder embeds its encoding and the selected transport, so its schema reaches every brief unchanged. The handoff carries the fields the primary interprets and its existing reconciliation rules: unresolved refutations stay unresolved, safety rulings reopen scope, duplicate groups only suggest merges, and changed or new mandatory claims need confirmation. The instruction budget drops the return reference from both primary paths and measures the file-transport brief under the verifier brief limit.

**Schemas and workflow.** `verifier-manifest/2` and `verifier-accounting/2` are retained. `return_file` appears in a manifest only under file transport, and `transport` and `repair_of` appear in a report only when they apply, so inline manifests and reports keep their shapes. An older helper refuses a file-transport manifest as an identity mismatch rather than misreading it. `v5b-24` is retained: verdicts, admission, verification triggers, batch allowance and public rendering are unchanged. The [demonstration](../../docs/research/review-code-verifier-transport-2026-09-23/README.md) replays #341's two verifier batches. Accounting is identical under both transports and matches the archive, the primary writes 2,162 and 3,315 fewer return characters, and its return instructions shrink by 2,525 bytes. The worker brief grows 155 bytes inline and 621–631 bytes under file transport. No limit rises.

## Continuation chain helper, issue #345, 2026-09-23

`continue_review.py` replaces the hand-written, unvalidated addendum. `state` reads a record's chain by its links, never by file names or timestamps. It validates each file against the state before it and prints the current state. `compose` takes the continuation's decisions and a `review_context.py --prior-head` store. It derives the identity, heads, record link, delta order, batch identity and cumulative allowance, and defaults `outstanding` and `routed` to the chain's. It then validates the whole addendum against the chain and saves it. The model still decides every delta file's state, each fixed finding's classification, new items, check evidence, tasks, status and coverage. None of those defaults.

**Validation.** Known schemas, the record link and schema, and `reviewed_head` links are checked. Forks, cycles and unlinked addenda are refused. Fixed ids must be open, and new ids must not be. Record row rules apply at the final head, and every task's ruling is checked against its batch's accounting report. The helper also checks mandatory confirmation, allowance that only grows, preserved `outstanding` and `routed` entries, and untouched per-file coverage, which only a replacement's own file accounting settles. An allowance written, as the base contract listed it, without `carried_from` reads as null. Status and coverage are checked against the cumulative open state, or, when the addendum names a replacement, the status against the replacement's own items. A replacement record must head the final head and carry the open items, routed items, outstanding work and spent flags, with `carried_from` naming the file it replaced. It must also carry the confirmation of each finding open before the addendum as `carried:<original chain file>#<batch>` with its trigger, so provenance survives any number of replacements. A finding the addendum or the replacement raised has no earlier chain file to carry from; the replacement confirms it in its own batch. Hand-written addenda are held to the same rules, so a chain that silently dropped state now reads as `chain-invalid`.

**Markers.** A new addendum carries `finalization` (`review-code-finalization/1`) naming `addendum-<final head>.report.md`. That complete current result is rendered through the finalizer's shared `ledger_sections` and linked into place last, and no file is ever replaced. An addendum whose named report is missing is an interrupted write: the chain is invalid until a continuation for the same final head replaces it. Chain files without `finalization` predate #342 and stay readable.

**Legacy.** A version-1 record or addendum returns `legacy-chain-needs-mapping` with the chain files in link order and the latest version-2 addendum's allowance, outstanding work and routed items as a floor. The prose mapping stays manual, as the issue required, and `compose` refuses the chain. Unreadable legacy state is `chain-invalid` instead. A version-2 replacement built from a mapped chain can be passed to the helper directly.

**Callers.** `finalize_review.py --compact` and `--check` print the gate's `continuation <absolute path>` line before the report, and pre-report gate records print it after `legacy`. `implement-publish` briefs continuations with that path and publishes only when `state` exits 0 at the final committed head.

**Schemas and workflow.** `implementation-gate-addendum/2` and `implementation-gate-record/2` are retained. `finalization` is additive on the addendum, as on the record, and the protocol string is its discriminator. The addendum's shape and key order are unchanged: the replay in [the demonstration](../../docs/research/review-code-continuation-composer-2026-09-23/README.md) saves bytes identical to #341's hand-written addendum. `v5b-24` is retained as well. What is open, cumulative or carried, admission, verification triggers, the allowance and public rendering are the rules `continuation-addendum.md` already stated; the helper enforces them. An unknown reported fixed id is still a coverage gap, now recorded under `coverage_gaps` because `fixed_findings` refuses it. The derived input drops 17 of 57 leaves, 12 of #341's 22 mechanical ones. `continuation-addendum.md` grows 194 bytes and the runtime total is 91,790 of 92,000, so no limit rises.
