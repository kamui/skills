# Review-code design

`review-code` inspects a pull request, a committed range, or a working tree, and it returns a validated review record. It does not publish. This file explains the current design for maintainers. [`SKILL.md`](SKILL.md) and its references define runtime behavior. The [design history](../../docs/review-code/HISTORY.md) lives outside the installed skill. It keeps earlier rules, experiments, issue evidence, dated design notes, and release notes. Rules there may have been superseded.

## Review and verification

One reviewer reads the pinned change and checks its stated requirements. The reviewer follows named risks into relevant unchanged code and tries to falsify each candidate before keeping it. This keeps the usual review in one context, and it still gives a missing requirement or a risk outside the changed lines a way into the review. Before deriving coverage, the reviewer accounts for every changed file, every risk check, and every required input.

The skill states what it adds to an ordinary review prompt. It reviews the promised outcome, follows consequences beyond the diff, has consequential claims challenged independently, and keeps a durable record across fixes. These are commitments about review behavior and handoff. They don't claim higher recall or precision than a built-in reviewer.

The rubric and the verifier instructions set evidence standards, and they leave the order of investigation and the proof strategy to the model. A ruling still needs decisive evidence. Conformance comes from the pinned artifact, compatibility stays separate from compliance, and a changed test needs meaningful assertions. Removing an existing test's protection against a regression is a correctness `must-fix` until the change or an authorized person explicitly accepts the loss. This rule overrides the `consider` cap on ineffective tests, because reviewers found such a lost protection and still approved the change under that cap. A missing extra assertion, a test that was already ineffective, or an optional extra case stays `consider`.

Independent verification is a separate step in a fresh context. A candidate that survives under a mandatory trigger becomes a required candidate task, and it needs a `confirmed` ruling before it can publish as a finding. When a review would find no blocker but the change touches a named safety area, the reviewer sends the concrete premises behind that conclusion as safety-premise tasks. The initial batch and the follow-up batch share one allowance. That allowance covers the review and any run that continues it from a prior record. The [verification-task change](../../docs/review-code/HISTORY.md#verification-tasks-and-version-2-private-records-issue-331) explains why the skill retired the former complete-ledger clean-verdict attack. A low-risk clean review can finish without an independent verifier. Its risk of a missed defect stays open for the [bounded comparison](../../docs/research/review-code-rewrite-2026-09-22/README.md).

The reviewer judges evidence, admission, priority, and whether a safety area applies. Scripts do the mechanical work. They fetch a pull request's forge inputs, build the pinned context, package verifier tasks and account for their returns, hash the packet's intent, and reject contradictory records. Finalization renders syntax and links from authoritative fields, so the reviewer doesn't assemble publication artifacts by hand. `review-code-publish` owns forge writes and their authorization, including the decision whether a merged target publishes.

The always-loaded boundary rule keeps a review going after a command is denied or refused. The reviewer tries an allowed alternative, or it records the missing evidence and continues to the report. Without this rule, some reviews stopped after one sandbox denial. The rule grants no execution permission and adds no phase.

## Current mechanics

`WORKFLOW` in `render_review.py` is `v5b-35`. It versions the semantics of admission, verification, rendering, and state. A change to any of them advances the workflow, so the duplicate-review shortcut can't reuse a review made under the old rules. The private schemas are `review-code-record/1`, `review-code-finalization/2`, `forge-fetch/1`, `packet-context/1`, `verifier-manifest/3` and `verifier-accounting/3`.

**Compact presentation.** The summary leads with the outcome and the findings. Routine context, detailed checks, observations, settled premises, and settled history collapse under `Review details`. Unresolved items, unfinished verification, and coverage gaps stay visible. Composition requires a finding's trigger, impact, and change as separate fields. The renderer combines their prose and the optional source without field labels. Payload validation checks for explanatory prose instead of rebuilding those fields from visible labels. The compact layout doesn't change the meaning of priority, action, hidden trailers, pinned coordinates, status, or publication events.

**One record.** Every run writes `record.json`, `payload.json`, `batch.json` and, last, `report.md`, whatever the target and whoever the caller. `render_review.py` derives each mechanical field that a saved input owns. These fields are the run identity from the store and the packet, `packet_context` from the packet, `supplied_inputs` from the caller's specs, the record's own paths, the spent allowance, the lineage, and each batch's name, phase, and raw return from its bundle and accounting report. The finalizer refuses an explicit copy that disagrees. It then composes and validates the payload, projects the advisory batch, and promotes the report last as the success marker. `--check` reads a record without changing it. With `--head` and `--lineage`, it checks the record against a caller's expectations. `--emit-batch --event` is the gating projection that `review-code-publish` runs. A private directory has one writer at a time.

`record.paths.skill_root` is the path the finalizer was invoked through, and the finalizer doesn't resolve symlinks in it. Publishers run `--check` and `--emit-batch` from the root a record names. A harness safety check can refuse to run scripts from an installed skill's symlink target, such as a synced folder on another drive, while it allows the installed path. The finalizer still accepts an explicit `skill_root` that names either path to the same directory.

**Prior records.** A local run from `prior_record` re-reviews a finalized record after fixes, and it writes a new, complete record in a new directory. A record from before `review-code-record/1` is not a prior record. For such a record, the caller reviews in full from the base with a new allowance and names the earlier record in coverage. The one-hop check refuses:

- a prior that is not a finalized local `review-code-record/1` of the same repository and base;
- an unclassified or unknown prior item;
- an open item that the run does not render again, or an open `must-fix` that it downgrades;
- a settled item rendered again;
- a dropped `outstanding` entry that no task, and no check recorded at the final head under its id, settled;
- a dropped `routed` entry that no task released, unless the item is unresolved or disputed and its settlement released the entry;
- a batch for a phase the prior spent, or spent flags below the prior's;
- a carried confirmation whose `confirmed_in` and `batch` differ from the provenance on the prior's own task, or whose accounting does not confirm it;
- an explicit lineage other than the prior's lineage plus the prior;
- a delta review from a prior that left a changed file `unreviewed`;
- a carried premise that the prior did not settle with the same id, area, text and head.

The check looks back only one record, so it can't see a second run that also continued from an ancestor. The caller therefore keeps its latest accepted record. It requires that record, and every earlier record it accepted, in the final record's lineage.

A `routed.unresolved` or `routed.disputed` entry leaves once its item is settled. The item can be settled in the run that classifies it `fixed`, `accepted` or `obsolete`, or in any later run. Without this rule, the run after the settling run could neither keep the entry, because its id was no longer a rendered or prior item, nor drop it. An open item keeps its entry. `routed.unrecoverable_inputs` names no item, so only a task releases it.

**Unfinished verification.** A record states two facts beside `coverage`. `files` is incomplete when a changed file is `unreviewed`. `verification` is incomplete when `outstanding` lists an item. `run.coverage` is incomplete only when `files` or `verification` is incomplete, so a review with unfinished verification still can't approve. `coverage_gaps` holds only unreviewed files.

Each `outstanding` item is an object with `id`, `claim` and `settled_by`. The summary lists these items under `Unfinished verification`, so a later pull-request review can carry or settle them. A gap tied to no file, such as a check that never ran, goes in `outstanding` with the check as its id. A local run keeps the entry until a task settles it, or until a check recorded at the final head under that id settles it with a result. The results that settle an entry are `accepted`, `reviewer-executed`, `pending` and `failed`. `unavailable` settles nothing. The finalizer refuses an outstanding entry in the old `<id>: <reason>` string form, and it refuses a `files` or `verification` fact that the record contradicts. An older prior record with string entries still loads. Its entries keep their ids, and its file rows supply its `files` fact.

**Delta reviews.** A delta review needs only the prior's `files` fact to be complete. A round that left verification unfinished therefore doesn't force the next round to review the whole diff again. On a delta review, the reviewer sends optional verifier tasks only when the delta touches security, data integrity, destructive migration, compatibility, concurrency or failover. Each optional candidate task on a delta review names that `area`, and the finalizer refuses one without it. The finalizer accepts failover there because `SKILL.md` lists it as a trigger, although the premise areas leave it out. Without this limit, every delta re-review challenged the safety premises of the whole pull request again.

The summary lists every settled premise, with the head that settled it, under `Settled premises` in the collapsed details. A `holds` premise task is settled at the reviewed head. A delta review copies each premise that the delta and new evidence leave alone into `record.verification.carried_premises` with its original head, and the next round reads the list again. A premise missing from the list is unchecked, so the reviewer still challenges a premise that no earlier round settled before approval. Only a delta review carries premises, and a carried premise can't share an id with a task in the same run. A local `prior_record` run may carry only a premise that the prior record settled with the same id, area, text and head. The finalizer can't check a pull-request run's list against the earlier review without parsing that review's body. That rule therefore stays an instruction, as it does for `Unfinished verification`.

**Supplied checks.** A CI job at the reviewed head settles the checks it runs. The reviewer doesn't rerun those checks locally, even when a caller asks, and cites CI instead. In the slowest sampled re-review, rerunning suites that CI had already passed at the same head took more than half the time. A passed job is `accepted`. For a failed job, the reviewer reads the log and reruns only the failing test, and the failure becomes a `must-fix` candidate. The reviewer records a running job as `pending` and doesn't wait for it. A job that doesn't match the obligation settles nothing, and the one-suite cap still applies. A pending required check doesn't block approval by itself, because the forge's merge rules already wait on required checks. `record.check_evidence` accepts `pending` at the reviewed head with a reason, and `pending` doesn't change the status. The rubric's check outcomes match `EVIDENCE_OUTCOMES` in `render_review.py`.

**Fetch.** `forge_packet.py fetch` runs the root query, every continuation, and each referenced issue through `gh`. It saves each response, records the calls in `fetch.json`, and writes `packet.json` with the same code that `normalize` runs. The packet and its digest are therefore the same whoever fetched. `fetch` saves a failed call, doesn't follow it, and names it as a gap. `fetch` passes `--repo` explicitly, so a fork checkout still reads the base repository. Issues that the pull-request body links need the packet first, so a second `fetch` call adds only those issues and rewrites `packet.json`. The rule that forge calls stay in `SKILL.md` has two recorded exceptions in [`scripts.md`](../../docs/agents/scripts.md), and `fetch` is one of them. `review-bot`'s token script is the other. No script records timing. Measurements read the timestamps of tool calls in the transcript.

**Duplicate identity.** `forge_packet.py` hashes the intent in the saved packet. The intent is the pull request's title and body, and each linked issue's coordinate, title, body, comment records, availability and completeness. The trailer carries that `packet_context` and `supplied_inputs=yes|no`. `shortcut` permits reuse only when the head, base, merge-base, workflow and digest match, neither run had issues or specs that a caller supplied, and `later-state` has nothing unsettled. Base equality fixes the guidance from the base branch, so the guidance carries no digest. Local runs have no digest.

**Verifier returns.** A brief assigns `return.json` inside its newly created bundle. The worker creates that file and replies with only its path, so the primary doesn't generate the same JSON a second time to save it. Accounting reads that path alone, and only as a regular file that it reaches through no link. An `--inline` build assigns no file. The primary then saves the inline response verbatim, as it also does when a worker's write fails.

Every build generates a fresh opaque `bundle_id`, stores it in the manifest, and prints it after the brief's return encoding. The worker copies the ID into its return, and a rebuild of the same input gets a new ID. The return assignment is a line that closes the brief's instructions, and the manifest binds the brief by hash. The builder creates the bundle directory, so nothing in it predates the build, and a return that another brief left there carries another `bundle_id`. Accounting refuses a bundle whose manifest no longer matches its input, its brief, or its printed ID, and it refuses a bundle that an older builder wrote. It withholds every task of a return whose `bundle_id` is not the bundle's. The finalizer requires each batch's accounting report to carry its bundle's ID and manifest hash. `--repair-of` records a repaired return's original, which must carry the bundle's ID. A refused handoff leaves no report, changes no ruling, and earns no batch. Structural success is only structural, and a repair grants no batch.

`account_verifier_return.py` drops an unknown or invalid correction field from the report's copy of the return and keeps the record accounted. If `corrections` is not an object, it drops the whole value. Each drop adds one violation that names what it dropped. The raw return file and its hash don't change. Because a drop is a violation, the helper exits 1, and verification already uses an exit-1 report for its accounted records. An invalid `id`, `verdict`, `basis`, `evidence`, `settling_fact` or safety ruling still withholds the record. Without this rule, one invalid optional field, such as `corrections.priority: "P4"`, left a confirmed required task unfinished and the review `Incomplete`.

**Open risks.** [#347's measurement](../../docs/research/review-code-artifact-savings-2026-09-22/combined.md) found no overall saving in cost or latency. It found more finalizer repairs under the stricter preconditions, verifier returns that were still inline under Claude Code, and primaries that still opened worker-only references. Epic #355 removes machinery instead of automating it further. Rewriting a finalized record in place after a later record names it in its lineage is unsupported. Nothing guards against it now that no addenda directory exists.
