# Review-code design

`review-code` inspects a pull request, committed range, or working tree and returns a validated review record. It does not publish. This file explains the current design for maintainers; [`SKILL.md`](SKILL.md) and its references define runtime behavior. The [design history](../../docs/review-code/HISTORY.md), kept outside the installed skill, retains earlier rules, experiments, issue evidence, dated design notes, and release notes. Historical rules there may have been superseded.

## Review and verification

One reviewer reads the pinned change, checks its stated requirements, follows named risks into relevant unchanged code, and falsifies candidates before retaining them. This keeps the usual review in one context while giving requirement omissions and risks outside changed lines a path into the review. The reviewer accounts for every changed file, risk check, and required input before deriving coverage.

Independent verification is a separate, fresh-context step. A surviving candidate under a mandatory trigger becomes a required candidate task and needs a `confirmed` ruling to publish as a finding. When a review would have no blocker but the change touches a named safety area, the reviewer sends the concrete premises behind that conclusion as safety-premise tasks. The initial and follow-up batches share one allowance across the review and any run that continues it from a prior record. The [verification-task change](../../docs/review-code/HISTORY.md#verification-tasks-and-version-2-private-records-issue-331) explains why the former complete-ledger clean-verdict attack was retired. A low-risk clean review can finish without an independent verifier; its missed-defect risk remains open for the [bounded comparison](../../docs/research/review-code-rewrite-2026-09-22/README.md).

The reviewer judges evidence, admission, priority, and whether a safety area applies. Scripts build pinned context, package and account for verifier tasks, hash the packet's intent, and reject contradictory records. Finalization renders syntax and links from authoritative fields, so the reviewer does not assemble publication artifacts by hand. `review-code-publish` owns forge writes and their authorization, including whether a merged target publishes.

## Current mechanics

Workflow `v5b-25` versions admission, verification, rendering, and state semantics. `review-code-record/1`, `review-code-finalization/2`, `packet-context/1`, `verifier-manifest/2` and `verifier-accounting/2` are the private schemas.

**One record.** Every run writes `record.json`, `payload.json`, `batch.json` and, last, `report.md`, whatever the target and whoever the caller. `render_review.py` derives the mechanical fields a saved input owns (run identity from the store and packet, `packet_context` from the packet, `supplied_inputs` from the caller's specs, the record's own paths, the spent allowance, the lineage, and each batch's name, phase and raw return from its bundle and accounting report), refuses an explicit copy that disagrees, composes and validates the payload, projects the advisory batch, and promotes the report last as the success marker. `--check` reads a record read-only and, with `--head` and `--lineage`, checks it against a caller's expectations. `--emit-batch --event` is the gating projection `review-code-publish` runs. A private directory has one writer at a time.

**Prior records.** A local run from `prior_record` re-reviews a finalized record after fixes and writes a new, complete record in a new directory. The one-hop check refuses a prior that is not a finalized local `review-code-record/1` of the same repository and base; an unclassified or unknown prior item; an open item not rendered again, or an open `must-fix` downgraded; a settled item rendered again; a dropped `outstanding` or `routed` entry no task settled; a batch for a phase the prior spent, or spent flags below the prior's; a carried confirmation whose `confirmed_in` and `batch` are not the provenance the prior's own task carries, or whose accounting does not confirm it; an explicit lineage other than the prior's plus the prior; and a delta review over incomplete prior coverage. One hop cannot see a sibling that continued an ancestor again, so the caller keeps its latest accepted record and requires it, with every earlier accepted record, in the final record's lineage.

**Duplicate identity.** `forge_packet.py` hashes the saved packet's intent: the pull request's title and body and each linked issue's coordinate, title, body, comment records, availability and completeness. The trailer carries that `packet_context` and `supplied_inputs=yes|no`. `shortcut` permits reuse only when head, base, merge-base, workflow and digest match, neither run had caller-supplied issues or specs, and `later-state` has nothing unsettled. Base equality fixes the base-branch guidance, so guidance carries no digest; local runs have none.

**Verifier returns.** A batch returns inline, or, with `--return-file`, through a worker-saved file the manifest binds; accounting reads that file without following links and withholds every task when it is absent, linked, moved or partial. `--inline-fallback` accounts a verbatim save after a failed write, and `--repair-of` records a repaired return's original. Structural success is only structural, and neither transport nor repair grants a batch.

**Open risks.** [#347's measurement](../../docs/research/review-code-artifact-savings-2026-09-22/combined.md) found no overall cost or latency saving, more finalizer repairs under the stricter preconditions, verifier returns still inline under Claude Code, and primaries still opening worker-only references. Epic #355 removes machinery instead of automating it further. Rewriting a finalized record in place after a later record names it in its lineage is unsupported; nothing guards it now that no addenda directory exists.

## One record, prior records and packet identity, issue #357, 2026-09-24

The staged `SKILL.md` is active, reconciled with #356's reference names: it keeps the issue-tracker read, the focused-test timing wrapper until #359, and names the context build arguments `targets.md` now carries. `compose_review.py`, `validate_review.py` and `finalize_review.py` merged into `render_review.py`; `continue_review.py`, `context_fingerprint.py`, `continuation-addendum.md` and their tests are gone. The `profile`, `return_format` and merged-target publication authorization inputs are gone, `fragments.md` had no consumer, and the retrospective Mode line reads only "Retrospective review of merged pull request". Workflow `v5b-25` covers the record, state, trailer and Mode-line changes. Older trailers carry no `packet_context` or `supplied_inputs`, so each open pull request gets one fresh review at its next run: a one-time duplicate-review miss.

**Removed rules and their replacements.** Each rule a removed mechanism enforced has a replacement check with a fixture in `test_render_review.py`, `test_render_composition.py`, `test_forge_packet.py` or `test_command_chains.py`, or is a deliberate behavior change below.

| Removed rule | Replacement |
| --- | --- |
| A chain file names the current record and links its reviewed head; forks, cycles and unlinked files are refused | `lineage` is derived as the prior's plus the prior, and an explicit copy that differs is refused; `--check --lineage` refuses a sibling fork against the caller's accepted records; a prior inside the run's own directory is refused, so no record lists itself |
| A chain file needs its finalization marker and report; unknown protocols establish nothing | The prior-record check and `--check` refuse a missing marker, another protocol or schema, and a missing report |
| One repository across the chain | The prior's repository, base ref and base SHA must match |
| A fixed id must be open, and a new id must not be | Every prior open item is classified once with its action, an unknown id is refused, an open item is rendered again under its id, and a settled one never is |
| Per-file coverage the delta did not reach stays as the chain left it | The new record accounts for every file of the pinned manifest, and a delta review needs the prior's coverage complete |
| Check evidence keeps its original head | The record's check-evidence rule, unchanged |
| A carried confirmation names its chain file and batch (`carried:<file>#<batch>`) | `confirmed_in` and `batch` must match the provenance of the prior's own task, transitively, and that record's accounting must confirm the id; the `carried:` form and `carried_from` are refused as retired |
| Spent allowance is cumulative and never reset; a follow-up needs the initial batch | The finalizer derives the flags from the prior's and this record's batches, refuses a lower explicit copy, and refuses a batch for a phase the prior spent |
| Outstanding work and routed items survive every addendum | They survive unless a task this run ruled on settles them; a carried confirmation settles nothing |
| A replacement record carries every open item, an open must-fix as must-fix, routed and outstanding work, spent flags and confirmations | The same rules hold for every prior-record run |
| An interrupted addendum is incomplete and a retry replaces it | Finalization stages every output and promotes the report last; a failure removes what it wrote |
| The finalizer refuses a digest the saved inputs no longer produce | `packet_context` is derived from the saved packet, and an explicit copy that differs is refused |
| The digest covers PR and issue text, comments with availability and completeness, specs and guidance | `packet_context` covers the PR and linked-issue intent and the set of linked issues; `supplied_inputs=no` in both runs replaces the spec identities; base equality fixes the guidance |

**Behavior changes.** A record from before `review-code-record/1`, including a version-1 or version-2 addenda chain, is not a prior record: the caller reviews in full from the base with a new allowance and names the earlier record in coverage, instead of mapping version-1 chains by hand. `continue_review.py state` is gone because the latest record is complete. `--check` accepts only `review-code-record/1`, not pre-protocol outputs. Local runs keep no digest; they never had a duplicate shortcut. Rewriting a finalized record in place after another names it is unsupported. A local `prior_record` run rechecks fixed findings itself, as continuations did, and spent allowance alone leaves a fixed ordinary finding complete; required verification that remains keeps coverage incomplete.

**Budget.** The always-loaded set falls from 31,989 to 29,873 bytes and the runtime total from 83,195 to 77,361; a first review of either target kind falls from 54,621 to 51,479, the required-verifier path from 67,129 to 64,086, and a pull-request re-review from 61,147 to 60,631. Their limits fall to the next thousand. The continuation path, 42,692 bytes under #356, becomes the re-review path at 60,631: a prior-record run is a complete re-review that reads `targets.md`, `prior-state.md` and the finalizer's example rather than an addendum procedure, so this path's limit rises from 43,000 to 61,000 as the one re-review limit. #359's removal of the fetch queries and timing wrappers from `targets.md` is expected to lower it.

**Exercise.** The [bounded exercise](../../docs/research/review-code-one-record-2026-09-24/README.md) ran the four archived #341 tasks against this change, with the continuation reseeded as a prior record, and the callers' local artifact paths without forge writes. It records observations, not recall, precision, cost or latency.
