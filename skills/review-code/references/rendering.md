# Rendering the review record

Load at `SKILL.md` step 5. `review-record.md` defines the fields, eligibility, status, coverage, and identity; this reference says what the reviewer authors for the composer, how the summary's coordinates are derived, and how a rejected comment is repaired.

## What the composer renders

`python3 scripts/compose_review.py --store <store> composition.json > payload.json` renders every repetitive syntax of the review from the reviewer's authoritative fields and authored prose, validates the result with `validate_review.py`, and prints the validator payload; `validate_review.py --emit-batch` then projects that payload unchanged, and `--render` prints its coordinate fragments for the final report. `python3 scripts/compose_review.py --example` prints the exact composition input, `--example --profile implementation-gate` adds the `record` section, and piping either through the composer prints the rendered result; the script's docstring documents every field.

Code renders the title line and its `[P<n>] [must-fix|consider]` tags, the labelled `Triggers when`, `Impact`, `Change`, and optional `Source` fields in order, the `consider` permission sentence `Closing this without action is a correct response.`, the question's `Evidence`, `Why it matters`, and `Change no code for this.` paragraphs, each hidden trailer, the status paragraph with its counts and `(advisory)` marker, the `Mode` line, the delta range, the `Reviewed` line, every index entry with its coordinate fragment, the body-carried prose and trailer of file-anchored items, the conditional sections, and the run trailer. Prose is copied byte for byte, code and suggestion blocks included; nothing is truncated, reordered, or dropped. The reviewer decides every semantic field and never assembles a payload, a batch, a trailer, or a coordinate link by hand.

A `Source` field is authored as prose at its ledger coordinate: `Issue #123, acceptance criterion 2.`, `pr-body/"<quoted phrase>".` or `pr-title` on a pull request, `commit-<sha7>/"<quoted phrase>".` on a local target, or an `artifact-` coordinate. A field label written inside a field's prose outside a code span or fenced block is refused as a second field; a label quoted inside a suggestion block is example text.

Composition always returns the advisory record and refuses a `summary.gating` input; the publisher selects any authorized gating event through `--emit-batch --event`. With `--profile implementation-gate` the composer validates the same composition by the same rules, requires the `record` section, and prints the local record `review-record.md` describes instead of the payload. The composer refuses, naming the field, any contradiction its fields expose or judgment they omit, and never resolves one; with `--store` it also refuses an anchor the pinned merge-base manifest or run identity contradicts. A non-zero exit prints violations at their composition-input locations and no payload. Prior items are accounted for in `Disputed` and `Prior findings` only; their thread replies are drafted under `re-review.md` and posted by the caller, never as new batch comments.

## Summary body

Keep the body useful without duplicating inline comments. The reviewer authors the status, the `Intent`, `Issue fit`, and `Coverage` lines, the ambiguities, and the coverage gaps; the composer renders the rest.

`Intent` restates the change's purpose from its sources, and `Issue fit` gives the ledger's outcome. With no originating issue (`issues=none`), `Issue fit` states that issue alignment was unavailable and names the source the ledger was built from — the pull-request title and body, the commit messages in a local range, or a user-supplied spec — and gives each `not-verifiable` promise its disposition. When the repository workflow requires an issue and none resolves, `Issue fit` explicitly says the ledger came from the change description and the missing issue renders as a whole-change `[Question]` in `Open questions`. Neither line repeats a `not-verifiable` claim as an established fact. On a local target the composer appends its own `Source` sentence to `Issue fit` from `run.issues`, `run.specs`, and `run.change_description`; the authored `issue_fit` supplies the ledger outcome.

The status paragraph is the semantic status in bold with the `(advisory)` suffix, which only the publisher's authorized `validate_review.py --emit-batch --event` projection removes, then the counts the items imply: must-fix findings, `consider` findings, open questions, prior items still open, and disputed prior findings, each named only when non-zero, or `no findings` for a clean review; a delta re-review appends the range `re-review.md` requires. Keep the ordinary summary near 200 words before conditional sections. A merged target adds a `Mode` line stating that this is a retrospective review of a merged pull request with publication disabled, or separately authorized when that authorization exists; the line is mandatory whenever `merged` is true. Conditional sections appear only when non-empty, in this order after `Findings`: `Open questions`, `Observations`, `Ambiguities`, `Unanchored findings`, `Disputed`, `Prior findings`, and `Coverage gaps`. `Ambiguities` names the contestable term, gives both supportable readings, and states which reading governed the run. `Disputed` lists each disputed prior item and `Prior findings` every other prior item, each as its stable id, its classification, and one line of evidence, so every prior item appears in exactly one of the two. A file-anchored finding or question the forge cannot carry inline renders its complete prose and trailer in the body, under `Unanchored findings` or `Open questions`, with its visible `(file)` coordinate kept so this transport fallback is not mistaken for missing evidence. A clean review says so briefly. Do not narrate other dropped candidates or add scores, effort estimates, generic praise, empty security/test sections, or repeated finding prose.

Trailer values are single ASCII tokens; every commit SHA in a trailer is the full 40 lowercase hexadecimal characters, and visible prose may abbreviate it. Issues are sorted `owner/repo#number` coordinates or `issues=none`. The caller reports forge URLs after publication without editing the review body.

### Summary references

Every finding and question entry in the body carries its anchor coordinate, and its fix coordinate when the fix differs, as the fragment `validate_review.py --render` prints for that item. With `summary.repository_url` set to the base repository's canonical web URL (`baseRepository.url` from step 1's batched fetch), a `RIGHT` line anchor, a file anchor, and a fix site each render as a Markdown link to the commit-pinned blob at the run head; a `LEFT` line anchor stays a code span, because the forge requires a renamed file's new path for it and that path may not exist at the merge-base. Without `repository_url` — every local target, or a forge whose URL shape is not GitHub's — every coordinate renders as a code span. Observation evidence and prior-finding references stay code spans because nothing records which revision their prose was read against. Prose elsewhere in the body, complete finding prose in `Unanchored findings` included, may use the word anchor freely but must not write a coordinate in the fragment's shape.

A file anchor's `side` comes from the **full pinned merge-base changed-file manifest**, never from a filename or the delta manifest: a `D` entry is `LEFT`, which links at the merge-base, the only revision the file exists at; a file present at head is `RIGHT`; and unestablished provenance is `UNKNOWN`, which renders as an unlinked coordinate while the item explains the missing evidence. `UNKNOWN` is file-only. A per-item revision override is invalid. With `--store` the composer derives an omitted file side from that manifest and writes it into the payload; where the manifest does not establish one revision, or without `--store`, it refuses the anchor until the reviewer names `side`.

### Anchors against the store

With `--store`, the composer checks the `review-context-store/1` envelope produced by `review_context.py`, then a working-tree run's `tree` and `head` against its saved `snapshot`, and reads identity and the full manifest from its `context` object. Line and file anchors name the manifest's `path`; a rename's `old_path` is provenance only. Deleted lines use `LEFT`, added lines use `RIGHT`, and modified or renamed lines may use either side at the manifest path. The composer checks those supplied line sides without choosing one or establishing hunk membership.

## Repair a rejected comment

When the caller reports a conclusive malformed-comment rejection, repair its anchor. If no valid anchor exists, move its complete visible finding prose into an `Unanchored findings` body section with the decisive evidence coordinate and optional fix coordinate. Change the composition input, re-run the composer to recompute counts, status, indexes, and the validated payload, then re-emit the batch, return the repaired record to the caller for its publication checks. Never drop a verified finding to make a batch succeed.

Before returning, confirm that the visible priority, action, change, and fix site agree with the trailer and forge anchor. Repair a mismatch; if a consistent valid inline form is impossible, move the complete finding to `Unanchored findings`. Never choose hidden metadata over visible prose or omit a verified finding.
