# Continuation addendum

Read when a caller asks for a continuation of an `implementation-gate` record after fixes.

A continuation reviews the delta from the chain's current head to a final head and appends `addendum-<final head>.json` to the current record's `addenda` directory; the record, its report and earlier addenda never change. The private directory has one writer at a time: start only after the review or continuation before it has exited. `<continuation>` is the absolute `continue_review.py` path the caller returned, or `scripts/continue_review.py` under the record's `skill_root`. Never reduce the chain by hand.

1. **Read the chain.** `python3 <continuation> state --json <record>` validates the record and each addendum by their links, and prints the current state: open findings and questions, per-file coverage, check evidence at its heads, tasks, confirmations, spent allowance, outstanding work and routed items. Exit 1 `chain-invalid` names what is missing, malformed, forked, cyclic, unlinked or dropped: report each line as a coverage gap and return `Incomplete`. Never start over, and never reset the allowance. Exit 1 `legacy-chain-needs-mapping` routes to Version 1 chains.
2. **Build the delta.** In a fresh private directory run `python3 scripts/review_context.py --merge-base <merge-base of the record's base SHA and the final head> --head <final head> --prior-head <current head> --base-ref <base> --store <private-dir>/store.json`; review `## delta-diff`.
3. **Write the decisions** to `<private-dir>/continuation.json` (`python3 <continuation> --example` prints the shape). Give every delta file a state: `reviewed`, `ignored` with a reason, or `unreviewed`; none defaults. Classify each reported fixed id that is open as `fixed`, `still-open`, or `not-verifiable` with one decisive `evidence` pointer; an unknown id is a coverage gap. Add new `findings` and `questions` in the composition input's shapes, changed `requirements` rows, `check_evidence` (carried results keep their original head), the `tasks` and `batches` this continuation added, and `status`, `coverage` and `coverage_gaps` for the final head. The helper derives identity, heads, allowance, and each batch's name, phase and raw return. `outstanding` and `routed` default to the chain's; a written list must keep every entry, except outstanding work a task here settled. A new finding under a mandatory trigger needs its `confirmed` candidate task here, within the remaining allowance.
4. **Compose.** `python3 <continuation> compose --record <record> --store <private-dir>/store.json <private-dir>/continuation.json` validates the addendum against the chain, writes it, and promotes `addendum-<final head>.report.md`, the complete current result, last. On exit 1, repair the input and rerun; a rerun replaces only an interrupted write. Return its output.

## Replacement record

When the delta is too large to inspect, run a full base-to-final-head review into a new `implementation-gate-record/2`, then compose the addendum with `replaced_by_full_review` naming it; the helper refuses a replacement that loses state, and later continuations continue from it. The new record carries the chain's current state:

- **Open state.** Every open finding and question, `routed`, and every `outstanding` entry.
- **Allowance.** The spent flags as the chain left them, with `verification.allowance.carried_from` naming the latest chain file by absolute path. Its own batches spend only what those flags leave.
- **Confirmations.** Each `confirmed` candidate task whose finding is still open, with `batch` rewritten to `carried:<chain file>#<batch name>`, where the chain file is the absolute path of the record or addendum whose `verification.batches` holds that batch; a task already carried keeps its reference. Never copy a bare batch name: it would resolve against the replacement's own batches. The composer reads that chain file and batch's accounting report, and refuses a carried confirmation they do not establish. A carried task keeps its `trigger`.

## Version 1 chains

A record or addendum written before workflow `v5b-23` is version 1 (`implementation-gate-record/1`, `implementation-gate-addendum/1`). The helper lists the chain files and, as `floor` lines, what the latest version-2 addendum recorded; the mapping may raise those, never lower them. Map the chain by hand into the current state: the record, then each addendum in link order, an item open until a later `fixed_findings` entry classifies it `fixed`. Never write a version-1 file.

1. **Open items.** The record's `items` plus every addendum's `findings` and `questions`, in chain order, as above. `routed` and version-1 `outstanding` entries carry over verbatim.
2. **Allowance.** Count the batches recorded across the record and every addendum: one or more sets `initial_spent`, two sets `follow_up_spent`. A version-1 `follow_up_spent: true`, or a version-2 addendum's `allowance`, also sets it. A reinterpretation never grants a batch.
3. **Clean verdict.** A version-1 `clean_verdict: outstanding` becomes the outstanding entry `v1-clean-verdict`. Discharge it with safety-premise tasks within the remaining allowance when the final-head review touches a high-risk area; otherwise close it as `superseded-by-v2-policy` with the reason in `coverage_gaps`. Never record it as `stands`.
4. **Confirmations.** A version-1 candidate row, or a finding a version-1 addendum added, whose `verification` is `independent-confirmed` counts as a `confirmed` candidate task naming the batch in that file whose raw return confirmed it. Its trigger is `must-fix` for a `must-fix` finding, the finding's `kind` when that is `security` or `compatibility`, and `optional` otherwise. A confirmation whose file records no batch is not carried: that finding needs confirmation again within the allowance, or stays in `outstanding`. Other version-1 ledger rows are ignored.

Write that addendum by hand as `implementation-gate-addendum/2` with `record_format: implementation-gate-record/1`, in the shape `compose` saves: the input's fields plus `format`, `workflow`, `record`, `record_format`, `reviewed_head`, `final_head`, `replaced_by_full_review`, each batch's `name`, `phase` and `raw_return`, and cumulative `verification.allowance`, `verification.outstanding` and `routed`. A full replacement is a version-2 record built from the mapped state under Replacement record; later continuations pass that record to the helper.
