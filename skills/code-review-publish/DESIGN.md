# v5a design and evidence

This document records why the v5a prototype differs from v5. It is not runtime instruction. `SKILL.md`, `references/review-rubric.md`, `references/output-contract.md`, and the conditionally loaded `references/verifier.md` are authoritative.

## Question this prototype answers

Can v5 retain its economical single-reviewer frequent path while recovering accurate questions and observations, checking high-risk clean verdicts, and making verification and rendering behavior deterministic enough to grade?

V5a keeps v5's integrated primary, per-candidate falsification ledger, consequence-triggered fresh verifier, action/priority separation, anchor/fix separation, complete-diff coverage, and atomic publication. It does not adopt v2's default parallel axes or N-version replication. A low-risk clean review still finishes with one reviewer.

Workflow identifier: `v5a-1`.

## Cost and safety bounds

- The frequent path remains one integrated reviewer. G3 adds a second context only for the intersection of a high-risk surface and zero surviving candidates.
- Candidate verification starts with one batch. N3 permits one follow-up batch only after the initial dispatch; later mandatory verification gaps fail closed as `Incomplete`.
- Clean-verdict verification attacks existing acquittals rather than searching for findings, preserving the verifier's narrow role and making its result attributable to a ledger entry.
- Questions require static unresolvability. Observations require a standing fact and are capped. These channels therefore expose useful uncertainty without weakening finding admission.
- Retrospective mode changes publication authority, not review rigor: it produces the same complete would-be artifact but performs no external write by default.

## Deliberate exclusions

- N-version primary replication and reconciliation remain a separate experimental direction.
- Model-tier splits remain unencoded because the runs did not test them.
- V2's parallel Code and Requirements finders do not become the default architecture.
- V5 remains untouched; v5a is a separate prototype package and workflow identity.

## Change notes

Entries below record post-prototype reorganizations. They do not change review behavior and do not increment `v5a-1` unless stated.

- **Re-review split into a conditionally loaded reference (issue #30).** `SKILL.md` section 4's body and the output contract's `Replies and prior state` section moved verbatim into [`references/re-review.md`](references/re-review.md), leaving pointers behind. Motivation is per-run token load: the re-review and prior-state machinery is dead weight on a first review, and `references/verifier.md` already establishes the conditional-load pattern. Pure relocation — no rule text changed, no workflow identifier change.
- **Mechanical pre-publication checks moved to a script (issue #31).** [`scripts/validate_review.py`](scripts/validate_review.py) now checks trailer grammar and commit-SHA width (F1.3), summary anchor coordinates (F1.4), finding field order (F1.5), priority/action/blocking combinations, question form, anchor shape, and the observation cap; `SKILL.md` step 5 keeps only the semantic judgments. No rule changed: every check is derived from `references/output-contract.md` and `references/review-rubric.md`, and where the two could disagree the reference text wins. Motivated by the token cost of a long model-executed checklist and by avoiding the failed-publish, repair, rebuild, retry loop.
- **Compact G3 ledger rows (issue #33).** The clean-verdict batch still receives every disposition from the run — filtering by risk surface is explicitly forbidden, since a cross-cutting acquittal is what the batch exists to attack — but a non-survivor row is now capped at a one-line claim, the kind, the one-word disposition, a one-line falsification reason, and one `path:line` evidence pointer. Survivor records are unchanged, as are the G3 trigger conditions and the batch's two allowed conclusions. Motivated by the token cost of the second context on a candidate-heavy run.
- **Output budgets on private records (issue #34).** `support` is capped at three one-line entries across `inspected`/`checks`/`uncertainty`, a satisfied requirement-ledger entry is one line, and the example YAML record is annotated as survivor-shaped. The non-survivor ledger-row cap was already added by the G3 change note above and is referenced rather than restated. Survivor records, the claim/support split, what is withheld from the verifier, and the published finding's ~160-word budget are all unchanged. Motivated by output-token pricing: these private artifacts are generated tokens, billed at roughly five times the input rate.
- **Digest determinism is regression-tested (issue #35).** [`scripts/test_context_fingerprint.py`](scripts/test_context_fingerprint.py) drives `context_fingerprint.py` through its stdin interface and pins key-order and array-order invariance, comment-id type normalization, sensitivity to every semantic field, an F1.1 guidance-membership fixture whose excluded entries change the digest, and rejection of malformed payloads. `context_fingerprint.py` is unchanged; no nondeterminism was found. Rationale: the step-2 duplicate-review short-circuit skips a whole review on a digest match, so its value depends entirely on two conforming runs reproducing the same digest.
- **Repo-wide peer-set search for drift candidates (handoff 6).** This entry, unlike the others, is a rule change: the rubric's propagation/synchronization-drift paragraph now requires establishing the peer set by a repository-wide, case-insensitive search for both the rule's old wording and its new vocabulary before comparing peers, and states that a directory-scoped or single-sentence sweep does not establish absence. The workflow identifier stays `v5a-1` because the change tightens execution of an existing mechanism rather than adding or removing one. Evidence: on the pinned target-1 run, the v5a reviewer stated the correct drift-sweep intent and then scoped its grep to `skills/shortlist/`, missing the `shortlist-narrow/SKILL.md:46` consumer drift that five other runs found; five fresh replicates plus one stubbed-obligation diagnostic run all repeated the miss — most via directory-scoped sweeps, one via a repo-wide but case-sensitive grep whose keyword the consumer states only in lowercase. The retained risk-check category ("external contracts … version skew") and this paragraph were verbatim-identical to v5's, so the miss was execution scope, not a dropped clause.
- **Cleanup from the review of the five changes above.** Three corrections, no rule changes. `SKILL.md`'s reference list no longer restates the step-4 pointer to `re-review.md` — the conditional load is stated where it fires, matching how `references/verifier.md` is handled. The output contract's pointer now says `re-review.md` defines the classification that *populates* the `Disputed` and `Prior findings` summary sections, which the contract itself still defines. And `validate_review.py`'s one-sentence observation check masks the abbreviations `e.g.`, `i.e.`, `etc.`, `vs.`, `cf.`, and `et al.` so they are not read as sentence breaks, with a passing fixture pinning it. For the record on issue #30's byte criterion: the re-review split shrank the always-loaded trio (`SKILL.md`, `review-rubric.md`, `output-contract.md`) by 1,402 bytes at its commit — the ceiling under a verbatim move is roughly 1.5k, not the 2.5k the issue asked for — and the load-bearing savings are the ~2.2k-byte `re-review.md` skipped on every first review plus the output-token caps of issues #33 and #34.
- **Widened, adversarial clean-verdict check (issue #44).** A rule change. G3's formal output — `disposition <id> does not hold; re-open it` — had never fired across two firings of the batch, for three separate reasons, and this entry addresses each. The trigger missed the case that mattered: on tokio, v2a acquitted the two branches carrying the shipped regression while a different candidate survived, and under a zero-survivor-only trigger that shape can never reach a verifier at all; related-acquittal mode now rules on those rows inside the batch that already runs. The brief let the verifier agree: on redis (Sonnet) it examined the exact false refutation, re-derived the same false premise, and "strengthened" it without ever tracing the branch where the premise fails; the five-step procedure now requires restating the premise, naming its falsifying condition, and tracing the opposite branch, and forbids a `holds` ruling that cites nothing the ledger row did not. And the value arrived through the wrong channel: on redis (Fable) the verifier returned `clean verdict stands` and put the decisive untraced branch in its one permitted observation aside, so only the primary's initiative turned it into the run's finding; a premise-contradicting fact is now a `re-open` by definition, and the primary may not downgrade one to an observation. Cost is bounded exactly as before — at most one initial batch plus one follow-up batch per run — because related-acquittal mode adds rows to an existing batch, never a context. Attack depth is then split by kind so the added tokens land where the corpus shows the failures: on both redis runs the decisive row was `concurrency` kind, and no `maintainability` acquittal was ever the missed defect. `performance` sits in the one-citation set because the issue's two enumerations of the four defect kinds — the relatedness test and the full-depth list — both exclude it, and no `performance` acquittal appears anywhere in the corpus; a later run showing one hide a defect is the evidence that would move it. Extrapolated from metered corpus runs rather than measured under these rules, the estimate is +10–30k tokens on a run with a survivor on a high-risk file and +20–40k on a high-risk zero-survivor run, against +30–60k before the split, and zero on low-risk clean runs. Evidence: [aggregate analysis §2 "G3 on redis"](../../docs/research/prototype-runs-aggregate-tests-1-4-v2a-v5a.md#the-four-highest-stakes-cells), [test 2 Sonnet v5a run](../../docs/research/prototype-runs-2026-09-01-test-2/v5a-run.md), [test 2 Fable v5a run](../../docs/research/prototype-runs-2026-09-01-test-2-fable/v5a-run.md), [test 3 addendum](../../docs/research/prototype-runs-2026-09-01-test-3/addendum-2026-09-03.md). The workflow identifier stays `v5a-1` here; issue #52 bumps it once after all v5b behavior changes land (tracking epic #62).
- **Read discipline for the primary reviewer and verifier (issue #66).** A rule change tightening read discipline across primary inspection and candidate verification. Diff reading is consolidated into one complete invocation (`git diff <merge-base>...<head> --unified=5`), split only when output limits force it; re-reading per file or via `git show` commits is barred unless a candidate's history check needs a specific commit. Enclosing-symbol bounded ranges around hunks become the default; whole-file reads require <=300 lines or a named candidate trace recorded in the private record, and files added by the diff are not re-read. Searches are batched across relevant paths rather than executed per file. The verifier similarly reads anchor and fix sites as bounded ranges at head and merge-base (`git show <merge-base>:<path>` with a line range), reading whole files only when an essential conditional cannot be located otherwise. Evidence: [test 4 v5a run](../../docs/research/prototype-runs-2026-09-01-test-4/v5a-run.md) Metadata (≈38 static reads of ≈77 tool calls on a 10-file +334/−1 diff; ≈14 git commands including per-file diffs and a full `git show` of the last commit), [test 3 v5a run §5](../../docs/research/prototype-runs-2026-09-01-test-3/v5a-run.md#5-every-file-command-script-or-external-doc-consulted-beyond-the-diff-manifest) (`pool.rs` "read in full at `review-head` (via `cat -n`), and the base version in full"), and [test 4 comparison data](../../docs/research/prototype-runs-2026-09-01-test-4/comparison-data.md) (v5a ~100 tool uses vs v5 ~63 on the same diff). Estimated savings: −15–30k tokens per run (−8–12%) on every `code-review-publish` run from fewer and smaller reads, −10–20 tool calls (−2–4 min wall clock), and −3–8k per verifier batch from bounded ranges. Quality risk is low: every recall miss in the corpus was a reasoning miss on code already read, never a failure to read enough; the 300-line exemption preserves whole small files, and any candidate can still open any file it needs. The workflow identifier stays `v5a-1` here; issue #52 bumps it once after all v5b behavior changes land (tracking epic #62).
- **Maintainer approval is not closure on unreleased public API; an explicit deferral reopens the question (issue #46).** A rule change to gate 6 ("Unintentional") and the rubric's issue-fit section, with a matching step-1 recording obligation. Approval, LGTM, or merge now establishes acceptance only of what the review record explicitly addresses; it is provisional for public API surface that appears in no released version at the merge-base; and an explicit deferral in the record ("we can fix this during the API review") is evidence the deferred question is open, so a candidate about it passes gate 6. Issue fit adds that whether unreleased API surface should exist in this shape at all is outcome-changing when a repository rule or an explicit deferral bears on it, routed as a question when static sources cannot settle it and as a repository-rule finding when a cited rule is contradicted. Step 1 records every explicit deferral of a design, naming, or API-shape decision with its author and the surface it concerns. Evidence: [test 4 v5a run](../../docs/research/prototype-runs-2026-09-01-test-4/v5a-run.md) ledger row A5 — the reviewer reached the real design problem (`removeCookies` is expressible as `cookies()` + `clearCookies()` + `addCookies()`, and upstream deleted it 24 days after merge) and dropped it because "the maintainer reviewed and approved this exact feature", while the packet carried the maintainer's own deferral ("`filter` would probably be a better name, but we can fix it during the pre-release api review"); [test 4 evaluation GT-2](../../docs/research/prototype-runs-2026-09-01-test-4/evaluation.md); [aggregate analysis §7 conclusion 11](../../docs/research/prototype-runs-aggregate-tests-1-4-v2a-v5a.md). Applied on paper to A5 under the new text: the deferral marks the API shape open, the surface is unreleased at the merge-base (`package.json` at `1.42.0-next`, the method tagged `since: v1.43`), and `CONTRIBUTING.md`'s "Avoid adding 'sugar' API" rule is cited, so A5 passes gate 6 and becomes a repository-rule candidate rather than a drop. Approval still closes what the record explicitly discussed and accepted, and a new API with no deferral and no contradicted rule is not reopened. Cost is near zero: a few hundred tokens of rule text plus extracting deferral sentences from comments the reviewer already reads, and occasionally one more candidate-batch row (~5–10k tokens) on a run where the rule creates a question or repository-rule candidate. The workflow identifier stays `v5a-1` here; issue #52 bumps it once after all v5b behavior changes land (tracking epic #62).
