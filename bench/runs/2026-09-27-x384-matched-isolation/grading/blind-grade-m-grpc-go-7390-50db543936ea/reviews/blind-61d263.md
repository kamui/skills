# Review blind-61d263

### Item 1
Location: clientconn.go:983-996
Claim: Unlock ac.mu before updateAddrs's deferred GracefulClose call. addrConn.updateAddrs is called with a changed address list while the addrConn already has a live ac.transport (e.g. state Ready, or reconnecting to a since-superseded address) -- a routine reconnection path, not a shutdown or error path.
Consequence: updateAddrs no longer unlocks ac.mu before returning. Its deferred `ac.transport.GracefulClose()` -- which synchronously calls the transport's onClose closure, which does `ac.mu.Lock()` -- now runs while ac.mu is still logically locked by this same goroutine, so the goroutine that called updateAddrs blocks until the independently scheduled `go ac.resetTransportAndUnlock()` goroutine happens to reach its own `ac.mu.Unlock()`. At the merge-base this deferred call always ran after an explicit `ac.mu.Unlock()`, so the caller never blocked here; grpc's own tearDown() still documents and follows exactly this ac.mu/GracefulClose ordering requirement (clientconn.go:1573-1575: "We have to release the lock before the call to GracefulClose/Close here because both of them call onClose(), which requires locking ac.mu."). The block is bounded -- resetTransportAndUnlock's pre-unlock work is pure computation, no I/O -- but it is a genuine, previously nonexistent synchronization dependency on the shared address-update path.
Fix: Before updateAddrs returns, unlock ac.mu explicitly (as at the merge-base) so the deferred GracefulClose always runs unlocked, and have the spawned reconnect goroutine acquire ac.mu itself at entry instead of assuming the caller's lock carries over; do not rely on the spawned goroutine's own unlock as the release mechanism for this goroutine's deferred call.
