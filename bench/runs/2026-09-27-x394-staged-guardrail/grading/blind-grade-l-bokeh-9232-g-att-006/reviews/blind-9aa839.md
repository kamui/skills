# Review blind-9aa839

### Item 1
Location: bokehjs/src/lib/models/widgets/date_picker.ts:82-85
Claim: _unlocal_date now shows the wrong day for negative-UTC-offset users. A DatePicker is rendered with a value/min_date/max_date coming from the server (e.g. `DatePicker(value=datetime.date.today())`, or any later Python-side `.value = some_date` assignment) while the browser's local timezone is behind UTC (`getTimezoneOffset() > 0`), e.g. any US/Canada/South America timezone.
Consequence: bokeh's Python side always serializes a `dt.date`/`dt.datetime` value as a UTC-midnight timestamp for the intended calendar day (bokeh/util/serialization.py:182-184). Before this diff, `_unlocal_date` read that timestamp's UTC calendar day via `toISOString()`, which is correct in every timezone. This diff instead shifts the Date by `-getTimezoneOffset()` minutes first (date_picker.ts:82-85), which extracts the Date's LOCAL calendar day. For any browser timezone behind UTC, a UTC-midnight instant's local calendar day is the day before the intended one, so the picker now displays one day earlier than the actual value for a very large population of users — reintroducing the exact class of bug this PR fixes for UTC+ users, in the opposite direction, on the more basic 'display a value set from Python' path rather than only the narrower post-selection round trip the PR targets. Reproduced directly: under TZ=America/New_York, applying the merge-base body to a Date.UTC(2019,7,30,0,0,0) instant yields 'Tue Jul 30 2019' (correct); applying the head body to the same instant yields 'Mon Jul 29 2019' (wrong).
Fix: Do not change _unlocal_date's general UTC-based extraction, which unrelated callers (the server-set value/min_date/max_date path) depend on for correctness in every timezone. Instead fix the actual defect: `_on_select` (date_picker.ts:95) stores the selected date as `date.toDateString()`, a string with no timezone marker; the next render() re-parses it with `new Date(this.model.value)` (date_picker.ts:68), which JavaScript parses as LOCAL midnight, not UTC — that mismatch, not _unlocal_date's UTC extraction, is what produced the UTC+ off-by-one. Fix that specific round trip (e.g. normalize/parse the stored string consistently, or track the picked calendar day separately from the UTC-timestamp path) so both the selection round trip and the server-set-value path read correctly in every timezone.
