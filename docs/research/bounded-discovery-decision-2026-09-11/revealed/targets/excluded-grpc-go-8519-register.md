# Defect register

## GT-q1: `TestHandlerTransport_HandleStreams_StatsHandlers` cannot fail for the race it is documented to catch

- **File/function/lines at pinned head:** `internal/transport/handler_server_test.go`, function `TestHandlerTransport_HandleStreams_StatsHandlers` (line 531 at `31a6f265`), specifically the `handleStream` closure at lines ~559–567, which calls `s.SetTrailer(...)` (line 563) and then `s.WriteStatus(st)` (line 566) sequentially in the same goroutine, with a single `mockStatsHandler` registered. Introduced by diff hunk in `5ed7cf6a` (and, before the "Use a new test" rework, by the near-identical version in `2fe9a4f8`).
- **Expected behaviour / violated intent:** the function's own doc comment states: "Tests the use of stats handlers and ensures there are no data races while accessing trailers." The task's own rubric: "A test that cannot fail for the reason it exists ... is a material defect of the test."
- **Trigger:** none needed to observe the defect — the test contains no concurrent mutation of `s.trailer` at all; `SetTrailer` and `WriteStatus` run back-to-back in one goroutine, so there is no interleaving for the race detector to catch regardless of whether `hdrMu` is held in `writeStatus`'s trailer-copy loop.
- **Demonstrated consequence (reproduced myself):** in a worktree of the merge commit (`5ed7cf6a`), I mechanically reverted only the diff's two added lines (`s.hdrMu.Lock()`/`s.hdrMu.Unlock()` around the `OutTrailer` copy loop, `handler_server.go:280` and `286`), leaving everything else — including the merged test — untouched, and ran:
  - `go test -count=200 -race -run 'Test/TestHandlerTransport_HandleStreams_StatsHandlers' ./internal/transport/` → `ok`, 0/200 failures.
  I additionally tried to construct an independent repro of the underlying race against the same reverted tree: (a) a goroutine calling `SetTrailer` in a tight loop concurrently with `WriteStatus` (200 iterations, `-race`) — no failure; (b) widening the internal race window by registering 5 stats handlers (matching the *original*, pre-"Use a new test" repro in commit `2fe9a4f8`, which did register 5 `mockStatsHandler`s) — still no failure in 200 iterations. This confirms the underlying race is a narrow-window race that is hard to trigger even when deliberately provoked (consistent with the original reporter calling it "quite intermittent" in production, see "Preexisting hints" below) — but it also means the merged test, exactly as shipped, gives zero empirical protection against a regression of this bug: it would stay green indefinitely even if the fix were reverted.
  - Sanity check the reverted tree isn't just broken outright: `go test -count=1 -race -run 'Test/HandlerTransport' ./internal/transport/` on the *unmodified* merge commit → `ok` (1.679s); same suite on the merge-base `0ebea3e` (pre-fix, pre-test) → `ok` (1.589s, obviously, since the new test doesn't exist yet at that commit).
- **Required corrective outcome:** the test must actually create the interleaving that makes the unlocked read a genuine data race — e.g., a second goroutine mutating `s.trailer` (via `SetTrailer`) concurrently with the in-flight `WriteStatus` call (not sequentially before it), and/or enough iterations/stats-handler multiplicity to reliably hit the internal `ht.do()`-closure vs. outer-loop window that the fix also closes. Any shape of test that fails under `-race` with the fix reverted and passes with it applied would discharge this; the current test does neither.
- **Category:** C3 (test the diff adds that is materially wrong). Does **not** fit the hypothesis's proposed C4 "clean control" framing for this specific artifact — the hypothesis treats "adds a regression test" as evidence of cleanliness; the test does not accomplish what a regression test needs to.
- **Relation to the PR's promise:** the PR's promised, user-visible behaviour is the 2-line lock fix (release notes: "Fix a data race while copying headers for stats handlers..."), which is correctly and sufficiently implemented (see below). GT-q1 is a separate, unintended shortfall in the *verification* the PR shipped alongside that fix, not a flaw in the promised fix itself.

# Not ground truth

Plausible-sounding objections that do **not** hold up, all explicitly raised in the hypothesis's list of "tempting objections":

- **Lock ordering between `writeStatusMu` and `hdrMu`.** Reviewer `arjan-bal` raised this in review (`internal/transport/handler_server.go:280`, review comment): "We're holding two locks here, this and `ht.writeStatusMu`... there shouldn't be a chance of deadlocks." Verified independently: `grep -rn writeStatusMu internal/transport/*.go` shows `writeStatusMu` is declared and used only inside `writeStatus` itself (`handler_server.go:165,229,230`), always acquired first with a single `defer Unlock()` for the whole function, and never re-entered or acquired from any other code path or while `hdrMu` is held elsewhere. No inversion is reachable. Not a defect.
- **Holding `hdrMu` while calling into stats handlers (`sh.HandleRPC`), risk of reentrant deadlock if a user's stats handler calls back into the stream.** This exposure is not new: the analogous `(*http2Server).writeStatus` (`internal/transport/http2_server.go:1078-1143`) holds `s.hdrMu` for its *entire* function body via `defer` (line 1079-1080), which also spans its own `for _, sh := range t.stats { sh.HandleRPC(...) }` loop at the bottom (lines 1136-1142) — i.e., the established, pre-existing pattern in this codebase already calls into stats-handler code while holding `hdrMu`. The PR's description cites this exact code as precedent. `stats.Handler` is documented ("Package stats is for collecting and reporting... monitoring purpose only") as a passive observer API, not one with a contract permitting calls back into the emitting stream. Not a novel risk introduced by this diff.
- **Copying `s.trailer` while still inside the lock (performance/contention concern).** The copy (`s.trailer.Copy()`) is O(number of trailer entries) and executed once per `WriteStatus` call per RPC; `hdrMu` is per-stream, so this cannot contend across RPCs. No demonstrated performance regression; not material.
- **Test determinism, as a general category of objection to any race-repro test:** partially true (see GT-q1) but for a more specific and provable reason than "you can't easily test races" — I demonstrated GT-q1 concretely rather than accepting it as unprovable/inherent. A reviewer who says "you can never reliably test a data race" would be overclaiming; the real, demonstrated defect is that this *specific* test has no concurrency in it at all, not that races-in-general are untestable.
- **The PR description's citation of `http2_server.go` lines 1140-1142 as showing "we do lock the mutex... in the regular gRPC server transport."** Read literally, those two lines are the `HandleRPC` loop itself and show no `Lock()` call adjacent to them. This is not incorrect, just imprecise: the lock is acquired 60 lines earlier (line 1079) and held via `defer` through the entire function, including that loop. A reviewer flagging "the PR's linked evidence doesn't show a lock" would be technically noticing something true about the citation's precision, but the underlying claim (http2_server.go already had this protected) is correct once the `defer` is accounted for. Not a code defect, and not a defect in the fix's reasoning — at most an imprecise citation in prose.
- **The five later commits touching these files** (`#8624`, `#8630`, `#8639`, `#9136`, `#9331`) — checked each via `git show --stat`/full diff. `ece73978`/`74b65af7`/`ab1ca089` are heap-allocation/performance refactors (the latter collapses `[]stats.Handler` into a single combined `stats.Handler`, preserving the exact `hdrMu.Lock()/Unlock()` pair around the (now singular) `HandleRPC` call — confirmed via diff). `1c8e0950` changes `Drain()` panic behaviour, unrelated to `writeStatus`/trailers. `7354d9c8` touches one unrelated line for buffering small data frames. None alters trailer-copy locking semantics or the `TestHandlerTransport_HandleStreams_StatsHandlers` test's structural weakness (which persists verbatim, sequential `SetTrailer`→`WriteStatus`, in current `master`, confirmed by inspecting `master:internal/transport/handler_server_test.go`).
