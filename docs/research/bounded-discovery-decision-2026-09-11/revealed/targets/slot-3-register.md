# Defect register

## GT-r1 — `RCOBStateMachine.createSnapshot`/`applyEntry` lock release lets a snapshot's recorded index and its serialized content diverge

- **Location at pinned head** (`282d01c5466d7694a098112a012097aa3a5dfaf1`), file `server/raft_chain_of_blocks_helpers_test.go`:
  - `applyEntry`, lines ~115–142: after mutating `sm.hash`/`sm.blocksApplied`/`sm.blocksAppliedSinceSnapshot` under `sm.Lock()`, the function does `n := sm.n; sm.Unlock(); n.Applied(ce.Index)` — the call into the node happens **outside** the state-machine's critical section.
  - `createSnapshot`, lines ~281–329: it builds `snapshotData` (a JSON blob containing `BlocksCount: sm.blocksApplied`, the count of blocks folded into the local hash) while `sm.Lock()` is held, then does `n := sm.n; sm.Unlock(); err = n.InstallSnapshot(snapshotData); sm.Lock()` — the actual hand-off to the node, which is what stamps the snapshot with an index, also happens outside `sm`'s critical section.
  - Diff hunks introducing this: the two hunks in `282d01c5466d7694a098112a012097aa3a5dfaf1` (`git show 282d01c5...`) that change `applyEntry` (`sm.n.Applied(ce.Index)` → `n := sm.n; sm.Unlock(); n.Applied(ce.Index)`) and `createSnapshot` (`err = sm.n.InstallSnapshot(...)` → unlock/call/relock around it).
- **Callee contract** (confirmed at merge-base, unchanged by this PR), `server/raft.go:1151` `func (n *raft) InstallSnapshot(data []byte) error`: under `n.Lock()`, it reads the node's *current* `n.applied` at the moment of the call and uses it verbatim as `snap.lastIndex`, i.e. "this blob of `data` corresponds to everything through index `n.applied`, whatever that is right now." That contract is stated in the callee itself, one hop from the diff: the snapshot's index is not a parameter chosen by the state machine, it's read live from the node.
- **Trigger / interleaving** (reachable without any external input, purely by scheduling): while the fuzz test `TestLongNRGChainOfBlocks` (`server/jetstream_cluster_long_test.go:193`, a 10-minute randomized-operations test that concurrently issues `Propose` and `Snapshot` actions against `RCOBStateMachine`) is running:
  1. Goroutine A runs `applyEntry(ce)` for index k: it locks `sm`, sets `sm.blocksApplied = k`-worth of state, unlocks `sm` — but has **not yet called** `n.Applied(k)`.
  2. Goroutine B (the test's `Snapshot` action) runs `createSnapshot()`: it acquires `sm.Lock()` (now free), reads the just-updated `sm.blocksApplied` (reflecting entry k), serializes `snapshotData` including that count, unlocks `sm`, and calls `n.InstallSnapshot(snapshotData)` **before** goroutine A's delayed `n.Applied(k)` call reaches the node.
  3. Inside `InstallSnapshot`, `n.applied` is still the pre-k value (say k-1), so the file written to disk is `snap.<term>.<k-1>` containing `BlocksCount: k`.
  4. Goroutine A then calls `n.Applied(k)`, advancing the node's own bookkeeping.
  - Result: a persisted/installed snapshot whose node-visible index (k-1) is **older** than the state-machine content it actually encodes (k blocks) — exactly "snapshots could contain new data but with an old applied index," the wording used in the fix's own description.
- **Demonstrated consequence**: on a follower loading that snapshot (`loadSnapshot`, line ~331, sets `sm.blocksApplied = snapshot.BlocksCount` directly from the mismatched blob) while the underlying raft layer still believes only entries up to the older index have been applied, the raft layer will replay/re-deliver entries beyond that older index that the state machine already folded into its hash via the snapshot — a double application that desynchronizes the block hash chain the test exists to verify, causing intermittent failures of `TestLongNRGChainOfBlocks`. This is not conjecture on my part: it is the literal rationale given in the follow-up pull request `nats-io/nats-server#6623` ("De-flake TestLongNRGChainOfBlocks", merged 2025-03-10, commit `e8f1ed021e8dbbf2a9aa59e9120ecd222eecce01`): *"The test became flaky due to the locking changes [from #6593], since it introduced a race condition where snapshots could contain new data but with an old applied index, making the test fail. … (This was purely a test issue)."* That commit is a **partial revert** of exactly these two hunks in `raft_chain_of_blocks_helpers_test.go` (confirmed by diffing `e8f1ed021` against `282d01c54`: `propose`, `applyEntry`, and `createSnapshot` are restored to hold `sm.Lock()` across the call into the node; `raft_helpers_test.go` and `raft_test.go`, the other two files #6593 touched, are untouched by the revert).
- **Required corrective outcome**: any sufficient fix must restore the property that a state machine's `createSnapshot` publishes to the node an index that corresponds exactly to the data captured in that snapshot, and that `applyEntry`'s state mutation and its `n.Applied(...)` call are not separably interleavable with a concurrent `createSnapshot`'s read of that same state and its `n.InstallSnapshot(...)` call — i.e., serialize "update sm state" + "tell node about that update" as one atomic step relative to any other thread doing the same on the shared state, for both the apply path and the snapshot path together. (The actual fix chosen — re-widening `sm.Lock()`/`defer sm.Unlock()` to span the calls into the node again — is one sufficient shape; any other synchronization achieving the same joint atomicity, e.g. a single dedicated goroutine serializing both apply and snapshot requests, would also count.)
- **Category**: C1∧C3 as stated above in "Category fit."
- **Is this the PR's promised behavior change, or an unintended error?** It is an **unintended error**, and importantly a piece of *unnecessary scope*: the PR's own stated motivation (avoiding `lockAll()`-vs-state-machine-lock deadlock, and fixing `TestNRGTermDoesntRollBackToPtermOnCatchup`) only requires the `newStateAdder`/`stateAdder` machinery in `raft_helpers_test.go`, because that is the only state machine used by `TestNRGTermDoesntRollBackToPtermOnCatchup` (`server/raft_test.go:945`, `rg := c.createMemRaftGroup("TEST", 3, newStateAdder)`). `RCOBStateMachine` (`raft_chain_of_blocks_helpers_test.go`) is used by a disjoint set of tests (`TestLongNRGChainOfBlocks`, `TestNRGChainOfBlocksRunInLockstep`, `TestNRGChainOfBlocksStopAndCatchUp`) that this PR's stated goal does not touch. The author applied the same "unlock before calling into the node" pattern to `RCOBStateMachine` by analogy/consistency, and that extra, unneeded change is precisely what regressed 11 days later.

# Not ground truth

- **"`n := sm.n; sm.Unlock()` is a data race on the `sm.n`/`a.n` pointer field."** False: `sm.n`/`a.n` is assigned once at construction and never reassigned (`grep -n "sm\.n = \|a\.n = "` over both helper files returns nothing), so reading it after taking a local copy under the lock, then unlocking, is safe with respect to that field itself. The real defect (GT-r1) is a *logical* ordering/atomicity problem between two independently-locked subsystems (the state machine's mutex and the raft node's own mutex), not a plain unsynchronized-memory-access race; `go test -race` would not by itself flag it, because every individual field access is properly synchronized under some lock — there is simply no longer one lock spanning both "compute the snapshot" and "hand it to the node."
- **"`stateAdder.propose` in `raft_helpers_test.go` no longer holds any lock across the call to `ForwardProposal`, so it must be equally broken."** Not demonstrated: `stateAdder`'s analogous changes (`propose`, `applyEntry`, `snapshot`) were *not* reverted by #6623, and no test failure or follow-up fix has ever been attached to them (`git log` on `raft_helpers_test.go` from `282d01c54` to current `main` shows no such fix). The tests that exercise `stateAdder.snapshot` (`server/raft_test.go:74-75,3709,5170`) call it as a deliberate, sequential test action rather than from a continuously-running concurrent fuzz loop racing against `applyEntry`, so the race window this PR opened is much narrower there and has not been shown to matter in practice. Asserting it as a second confirmed defect would be spec-shaped pattern-matching without a demonstrated consequence.
- **"The PR should not have added `time.Sleep(100 * time.Millisecond)` to `TestNRGTermDoesntRollBackToPtermOnCatchup`; sleeps in tests are a smell."** True as a style observation, false as a material defect: the sleep follows an explicit `nc.Flush()` and exists to wait for interest propagation across the cluster before publishing the append entry that triggers the catchup path under test — exactly the race the PR states it is fixing. It is a hygiene point, not a correctness, security, data-integrity, compatibility or requirement failure.
- **"Deadlock risk from `rg.lockAll()` vs. state-machine locks, cited in the PR body, is itself unresolved."** Not evaluated as a defect here because the PR's own stated goal is precisely to *fix* that deadlock risk in `stateAdder`, and no evidence (revert, follow-up bug, hang report) exists that this part of the change is insufficient; #6623 only reverted the `RCOBStateMachine` hunks, not the `stateAdder` ones. Absent a demonstrated consequence, this remains the PR's promised, apparently-successful behavior change, not a leftover defect.

# Static visibility

Yes. A careful reviewer of the diff alone, holding `server/raft_chain_of_blocks_helpers_test.go`'s new `applyEntry`/`createSnapshot` bodies against two callee hops — `raft.Applied` and `raft.InstallSnapshot` in `server/raft.go` (one hop: read what the node does with the call) — can see directly that `InstallSnapshot` (`server/raft.go:1151`, unchanged by this PR) stamps the snapshot with whatever `n.applied` happens to be *at call time*, and that the diff moved the call to `n.InstallSnapshot` (and to `n.Applied`) outside the `sm` critical section that captured the data going into it. No telemetry, fuzzing, or long-running observation is needed to see that this breaks the implicit invariant "the index recorded with a snapshot matches the data in it" whenever a concurrent `applyEntry` interleaves between the unlock and the node call — only the demonstrated-consequence step (does this actually happen and does it actually break a test) benefited from the follow-up PR, which is used here as corroborating primary-source evidence rather than as the sole source of the finding.
