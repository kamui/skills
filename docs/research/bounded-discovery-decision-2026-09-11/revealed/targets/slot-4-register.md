# Defect register

## GT-s1 — The "fix" recaptures the same, already-unchanging pointer, so it does not close the race it claims to fix

**Location at the pinned head** (`b81b039c38afe724534ef6a1b9df490c5cdfaca4`): `server/stream.go`, `func (mset *stream) setupMirrorConsumer() error`, the two touched lines are (line numbers as introduced by this diff hunk):
- `mirror := mset.mirror` / `mirrorWg := &mirror.wg` (top of the function, right after the "no longer leader" early-return, under `mset.mu`).
- `mirrorWg.Wait()` inside the `go func() { ... }()` launched near the end of the function (was `mirror.wg.Wait()` before this diff).

**Diff hunk that introduces it**: the sole hunk of `b81b039c3` (`+mirrorWg := &mirror.wg` and `-mirror.wg.Wait()` / `+mirrorWg.Wait()`).

**Expected behaviour / violated intent**: the PR's own title and body state the goal: "Fixes a data race with `mirror.wg.Wait()`, while the lock is not held," and quote a `-race` trace showing a read/write race at that call site across two different goroutine instances of the same closure (`setupMirrorConsumer.func7`), at what was pre-fix line 3304 (`mirror.wg.Wait()`) and pre-fix line 3371 (`mirror.wg.Add(1)`, reached via a *shadowed* re-read `mirror := mset.mirror` further down in the same closure, inside `case ccr := <-respCh:`). The stated contract is: the retry goroutine must wait on the WaitGroup belonging to the mirror's *current* `sourceInfo`, without racing another goroutine's concurrent `Add`/`Wait`/`Done` on the same `sync.WaitGroup`, and (per the follow-up PR's own restatement of the requirement) must recognize when the mirror configuration has been removed in the meantime rather than blindly waiting on a stale one.

**Why the diff does not do this — verified directly by reading the whole function** (no external hop needed): the outer local variable `mirror` (`mirror := mset.mirror`, captured once near the top of `setupMirrorConsumer`, under `mset.mu`) is **never reassigned** anywhere else in that invocation of the function before the `Wait()` call. `mirrorWg := &mirror.wg` computed immediately after that capture, and `mirror.wg` referenced later at the `Wait()` call site, are therefore *the same memory address in every execution*, whether or not the extra variable is introduced. Adding `mirrorWg := &mirror.wg` one statement after `mirror := mset.mirror` and later writing `mirrorWg.Wait()` instead of `mirror.wg.Wait()` changes nothing about *which* `sourceInfo`'s WaitGroup is waited on, because there is no reassignment of `mirror` between those two points to protect against. I verified this by extracting the full function body (`git show b81b039c38afe724534ef6a1b9df490c5cdfaca4:server/stream.go`, lines ~3109–3450) and enumerating every occurrence of the identifier `mirror` in it: the only reassignment is a `:=` **inside** the `case ccr := <-respCh:` block (`mirror := mset.mirror`, re-read under the lock), which shadows the outer variable in a nested scope and executes strictly *after* the `Wait()` call, so it cannot affect it. Consequently the change is a provable no-op with respect to the exact race the PR quotes: it does not add a lock re-acquisition, does not add a "was the mirror config removed" check, and does not change the timing of when the address is computed relative to when it is used.

**Trigger**: any interleaving where `mset.mirror` is mutated concurrently, under `mset.mu`, by a different goroutine while `setupMirrorConsumer`'s own asynchronous retry goroutine is between its early capture of `mirror`/`mirrorWg` and its `Wait()`/`Add()` calls. Concretely verified code paths that mutate `mset.mirror` from other call sites, all requiring only `mset.mu` (not any special serialization with the in-flight goroutine): stream config update that removes the `Mirror` field (`mset.mirror = nil`, guarded by `if mset.isLeader()` in the stream-update path, `server/stream.go:2296` at head) and stream stop/delete (`unsubscribeToStream`: `mset.cancelSourceInfo(mset.mirror); mset.mirror = nil`, `server/stream.go:4421` at head). The upstream follow-up additionally names "a leader change and this server not being leader anymore" as a real-world trigger. Any of these racing against an in-flight `setupMirrorConsumer` retry goroutine reproduces the same class of unsynchronized concurrent access to the WaitGroup embedded in a `sourceInfo` that may no longer be the one `mset.mirror` points at.

**Demonstrated consequence**: this is not a hypothetical — it is directly confirmed upstream. [`nats-io/nats-server#7716`](https://github.com/nats-io/nats-server/pull/7716) ("[FIXED] Mirror consumer data race", commits `fb7c42e21b690663bfe71d6b2792bfcb01951f95` / merge `49e9e7b27ff2da7dc2b38ff38eb3f7810f91a567`, merged 2026-01-12) opens with: *"Follow-up to #7395, since Antithesis still manages to reproduce the data race. Instead of capturing the mirror's `WaitGroup` outside the goroutine, let's capture it in the goroutine itself which allows to check the mirror config hasn't been removed in the meantime (for example due to a leader change and this server not being leader anymore)."* This is the same author (Maurice van Veen) admitting, three months later, that the identical class of race was reproduced again by the project's continuous fuzzing (Antithesis) after #7395 had already been merged as "[FIXED]". The actual fix in #7716 is materially different from #7395's: it deletes the early `mirrorWg := &mirror.wg` capture entirely and instead, at the point of waiting, re-acquires `mset.mu`, checks `if mset.mirror == nil { return }` (bail out if the config was removed), and only then derives `wg := &mset.mirror.wg` and calls `wg.Wait()` after releasing the lock — i.e., the capture is moved to be as late as possible and is guarded by a fresh, lock-protected liveness check, which is exactly what #7395's diff described doing but did not actually implement.

**Required corrective outcome**: any sufficient fix must ensure that by the time the retry goroutine waits on (or later mutates) a mirror's `WaitGroup`, it does so only after re-checking, under `mset.mu`, that `mset.mirror` still refers to that same `sourceInfo` (or bailing out if it has been removed) — i.e., the wait target must be re-validated at the time of use, not fixed at a point in time before the goroutine yields the lock. #7716's patch is one sufficient shape; a differently-shaped fix (e.g., comparing a generation/epoch stored in the `sourceInfo`, or storing the `sourceInfo` pointer itself and checking `mset.mirror == capturedMirror` under lock before waiting) would also satisfy this outcome.

**Category**: **C1** — a concurrency/liveness defect in the retry-wait mechanism that the diff's own hunk edits (capturing and waiting on a `WaitGroup` across a goroutine boundary without lock-protected revalidation). It fits the hypothesis's named category.

**Is it the promised behaviour change, or an unintended error, or an insufficient implementation of a promised fix?** It is an **insufficient implementation of a promised fix**: the PR is explicitly titled and described as fixing this exact data race, includes the `-race` trace it claims to resolve, and was merged and shipped as "[FIXED]"; the change is provably inert against that trace (see analysis above), and the same race was independently reproduced and re-fixed under the same title three months later.

# Not ground truth

- **"`mirror.wg.Wait()` unlocked is inherently wrong / the lock should be held across the whole goroutine."** Not by itself a defect: the comment directly above it ("Wait for previous processMirrorMsgs go routine to be completely done. If none is running, this will not block.") documents *why* it must be unlocked — holding `mset.mu` across a `Wait()` that can block on another goroutine which itself needs `mset.mu` (see `processMirrorMsgs`, which takes the lock at its start) would deadlock. The mechanism of waiting without holding the lock is intentional and not itself the defect; the defect is specifically that the *pointer being waited on* is not revalidated against the current `mset.mirror` at the time of the wait.
- **"The shadowed `mirror := mset.mirror` inside `case ccr := <-respCh:` is a bug (variable shadowing)."** This is ordinary, intentional Go idiom here: it re-reads `mset.mirror` fresh, under the lock, specifically to pick up any change and to check `if mset.mirror == nil { return }` immediately beforehand. It is not the same as the earlier, unguarded capture, and is not itself defective.
- **"`sourceInfo.wg` should be a pointer, not an embedded `sync.WaitGroup`, so it can't be silently reused."** A plausible different design, but not a demonstrated defect in this diff: reuse of the embedded `WaitGroup` across sequential mirror-setup attempts for the *same* `sourceInfo` object is the existing, unchanged design from before this PR and is out of scope for what this three-line diff needed to fix.
- **"The PR added no test, so it should not have been merged."** True as an observation about process, but per the task's own definition a missing-test hygiene complaint is not itself a material defect; it does, however, explain why the insufficiency (GT-s1) went undetected until Antithesis found it independently.
- **"`isLeader()` is checked before capturing `mirror`, so a leader change can't happen after that point."** False as a defense but also not itself a new defect to raise: the check is a point-in-time snapshot under the lock; nothing prevents `mset.mu` from being released (implicitly, since `setupMirrorConsumer`'s synchronous portion ends and its caller unlocks) and the leader status or `mset.mirror` from changing before the spawned goroutine's `Wait()` executes. This is exactly restated as GT-s1, not a separate point.

# Static visibility

Yes, fully statically visible, and at less than the "two hops" budget: the entire argument for GT-s1 is contained within a single, unchanged function (`setupMirrorConsumer`, ~340 lines) that already exists at the merge-base and is only touched by a 3-line diff. A careful reviewer who read the whole function (not just the diff hunk) rather than the immediate `+`/`-` lines could mechanically verify that the local variable `mirror` is never reassigned between `mirrorWg := &mirror.wg` and `mirrorWg.Wait()`/the old `mirror.wg.Wait()`, and therefore that the new indirection changes nothing observable. Establishing the *trigger* (concurrent mutation of `mset.mirror` from elsewhere) requires looking at exactly one callee/contract hop beyond the diff: the two other `mset.mirror = nil` sites (`server/stream.go`, the stream-update path and `unsubscribeToStream`), both in the same file, both reachable by a simple grep for `mset.mirror =`. No telemetry, fuzzing, or execution was needed to establish the defect — only reading the full function plus grepping the same file for the other writers of `mset.mirror`. (Confirming that Antithesis *did* in fact re-trigger this specific race, rather than merely that it plausibly could, does rely on the follow-up PR's primary-source text — that part is not derivable from static reading alone, but static reading alone is sufficient to identify the defect and its shape.)

# Adjudicator's confidence and limits

High confidence in GT-s1 as stated. The core claim — that `mirrorWg := &mirror.wg` computed immediately after `mirror := mset.mirror`, with no intervening reassignment of `mirror`, is byte-for-byte equivalent to computing `&mirror.wg` at the later `Wait()` call site — is a mechanical fact about Go variable scoping that I verified directly against the full function body at the pinned head, not an inference. The claim that the underlying race persisted after this PR is not my own conjecture either; it is the literal, dated statement of the same author in the follow-up PR they filed, which I fetched directly via `gh pr view 7716`.

What remains genuinely `unresolved`, and does not change the verdict: the *exact* memory-level mechanism the `-race` detector used to label one `Wait()` a "write" (sync.WaitGroup's internal atomic state-word reuse across the documented "Add with positive delta when counter is zero must happen-before Wait" ordering requirement) is my best reconstruction from the quoted trace and Go's documented WaitGroup semantics, not something I reproduced with my own instrumented run in this session. This does not affect the verdict because the load-bearing evidence — the diff's provable no-op nature, and the upstream follow-up's explicit "still manages to reproduce" admission — holds independently of the precise WaitGroup-internals explanation. If a reader wanted this nailed down further, the way to settle it would be to run the Antithesis-style workload (not available here) or to instrument `sync.WaitGroup` reuse directly with a targeted stress test that creates and tears down a mirror's `sourceInfo` under concurrent load while another goroutine is mid-`Wait()` — outside this session's time/tool budget.
