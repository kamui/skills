## Recommendation

Keep `/code-review-deep-publish` as an explicit, selective independent-discovery review. Keep the standard reviewer as the default. Deep's strongest demonstrated benefit is finding omitted obligations and external-contract gaps through a separate Requirements investigation. Its high-risk positioning is a hypothesis worth testing, not an established safety advantage.

Separate its two purposes: preserve exact historical snapshots as benchmark comparators, and let the usable skill improve. A live skill should not retain weaker verification or publishing rules simply to remain architecturally distant from another skill. Preserve independent discovery; converge on reliable evidence, state handling, and publication mechanics. The current [design pole](../../skills/code-audit-publish/DESIGN.md#the-pole-statement) mixes these purposes and should be rewritten. Its claim that integrated reviewers cannot express questions is also obsolete: current publish has an explicit question channel.

The next release should first repair verification completeness and scope, then improve transport and output reliability, then test deeper discovery. Do not expand routine use before measuring that release. Replace the README/frontmatter's single cost multiplier with a qualified historical measurement and an instruction to measure actual run cost.

The record explicitly permits billed comparisons within a target and says costs across different targets are not comparable. The commonly quoted pooled $8.88 versus $3.62 (about 2.5×) mixes six Panel runs on two targets with eighteen v5b rows including cheaper publication/probe rounds. The skill's advertised roughly 1.5× *token* premium is an older, different metric and should not be presented as a contemporary billed-cost estimate. Mandatory verification did not guarantee precision. One of six Panel runs published a false P1 `must-fix` about `ExpiryT`: the verifier escalated a documented tolerable typing convention while overlooking that the runtime behavior predated the change. No false finding was recorded for v5b's fifteen retrospective runs, although it had misses and priority errors. This is a small sample with unequal target coverage, not a population precision estimate. [False finding adjudication](prototype-runs-holdout/evaluation.md#c-pythontypeshed9458--gt-c1-the-missing-re-export), [v5b criterion 1](prototype-runs-holdout/evaluation.md#success-criteria-for-v5b).

Finder-output validation was a measured operational problem: nine of twelve Panel finder reports triggered it; two runs remained incomplete after the allowed retry. At uv seed 1, bare-path evidence fields caused incompleteness despite substantive findings/questions. Repairing mechanically expressible report shape without rerunning discovery is therefore a concrete efficiency/reliability candidate; shape correctness should stay distinct from judgment or epistemic completeness. [Cost discussion](prototype-runs-holdout/evaluation.md#cost), [uv failure description](prototype-runs-holdout/evaluation.md#d-astral-shuv4424--gt-d1-the-deferred-naming).

The comparison-data `Wall` column sums agent transcript spans and can overlap in a parallel Panel; it should not be described as user elapsed latency. The evaluation quotes 49–93 minutes and also describes the cheapest run as 24 minutes of agent time. These records are insufficient for a clean latency multiplier. Collect start/end events around the whole review in the next test, as the current method requires. ## What the next decision needs

Current `legacy reviewer` declares `workflow=v5b-2` and includes changes after the holdout's `2f06662` (`v5b-1`), so these results cannot establish that today's integrated reviewer still has the same discovery/admission gaps. The new one-shot method distinguishes repaired-current versus historical experiments and a later separate discovery experiment; it reports no executed experiment or new results. Known Hyper, Typeshed and Cobra examples are regression fixtures, not fresh holdouts. Current output contract (historical source path omitted), [one-shot method](code-review-one-shot-method.md#1-freeze-the-experiment).

Recommended decision: keep deep as an explicit opt-in and standing comparator while improving its concrete operational weaknesses; do not expand default use merely on the label “high risk.” For an adoption/retirement decision, compare exact current snapshots on fresh matched PRs with isolated execution enabled, equal budgets, explicit model/effort pins, independent truth, actual whole-run latency and complete attempt accounting. Evaluate unique material recall, false findings, false-clean reviews, completion and cost separately. Include requirements-heavy cases where it has evidence and high-risk behavioral cases where its promise remains unproved. This recommendation follows the observed niche and the repository's current evaluation discipline, rather than treating extra agents or mandatory verification as quality guarantees. ## How to use the two skills

| Situation | Recommended use |
| --- | --- |
| Routine implementation PR, ordinary defect fix, bounded follow-up | the standard reviewer. |
| Dependency/version conformance, public API completeness, multi-artifact contract propagation, broad requirements likely to omit unchanged consumers | Explicit `/code-review-deep-publish`; this is its best-supported niche. |
| Concurrency, authorization, destructive migrations or integrity-sensitive changes | Deep is an opt-in additional discovery investment. First ship the verification repairs above; evaluate this niche before describing deep as more reliable here. Size alone is an inadequate routing rule. |
| Routine review completed, but independent discovery is still warranted | Freeze deep's first candidate inventory before showing it routine conclusions. Then reconcile prior findings/ids and thread state before publication. Do not routinely pay for two whole reviews or create duplicate comments. |
| Evaluation/comparator run | Pin the exact historical or current snapshot; publication disabled. Never freeze the live skill merely to keep a benchmark arm different. |

Deep should occupy the reviewer slot, not become an automatic extra stage after routine review. Both should present one coherent author-facing review and compatible actionable findings. Shared publication semantics are desirable; independent installation means any shared implementation must be packaged with each skill or otherwise explicitly supported, not referenced through an assumed sibling installation.

## Future features that earn the extra work

1. **Expected-surface discovery.** Have Requirements enumerate expected exports, commands, schemas, versions, platforms and behavioral obligations from authoritative inputs before inspecting compliance. Map each obligation to its implementation, including unchanged or absent files. Go beyond name presence: check signatures, conditional availability, defaults and semantics. This generalizes the measured Typeshed mechanism; it is stronger than another pass over changed files.
2. **Guarantee and transition audit.** Give Code a focused investigation of the changed guarantee: enumerate actors, states and transitions; compare base/head protection; trace normal operation as well as failure, shutdown, cancellation, retry and rollback. Produce counterexamples or bounded evidence, not generic security checklists. Requirements independently checks the corresponding user-visible promises.
3. **Executable evidence and repair sufficiency.** Permit proportionate changed-test execution and isolated minimal reproducers, with base/head comparison when needed to attribute a failure. After establishing a defect, check that the proposed remedy closes all demonstrated sibling paths. Do not mechanically run the same suite in every worker or require a long prose trace for every passing test.
4. **Discovery coverage beyond file coverage.** Keep the changed-file manifest, and add a compact map from expected obligations and risk boundaries to checked paths, evidence and gaps. Separate “every changed file inspected” from “all relevant expectations investigated.” An empty candidate ledger cannot reveal hypotheses neither finder considered.
5. **Measured escalation and reconciliation.** Record which finder discovered each unique actionable defect and the marginal cost of the second pass. Test whether a bounded independent challenger on selected surfaces can match the full two-finder approach. Freeze its discoveries before revealing primary conclusions; retain full admission and confirmation before publication. This is an experiment, not a reason to add more workers immediately.

These are investments in independent search scope and decisive evidence. Routine review can adopt successful techniques too; deep's distinction should be its deliberate second discovery pass and larger justified investigation budget, not exclusive ownership of sound review rules.

Release sequence: repair verification completeness/safety with a workflow bump; align publication/state mechanics and simplify report serialization; introduce expected-surface and transition discovery in separately measurable changes; then compare current snapshots on fresh tasks. If improved routine review matches deep's per-run material-defect recovery at lower cost without worse false findings or false-clean outcomes, retire deep as a normal user-facing command and retain its frozen comparator. Repeated useful incremental recovery justifies keeping it, with routing limited to the surfaces where that value appears.
