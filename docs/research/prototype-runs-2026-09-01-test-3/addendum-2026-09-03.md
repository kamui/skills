# Addendum — v2a and v5a run, `tokio-rs/tokio#7757` (2026-09-03)

> **Dev-set caveat, read first.** v2a and v5a were designed after their authors saw all three
> targets' results — all three tests (this one included) are development-set for them. This run
> verifies that specific, previously-diagnosed mechanisms fire as designed; it is not holdout
> evidence of overall quality, and a single run of each (n=1) cannot separate systematic behavior
> from sampling noise on any item it doesn't already have prior-round data for.

## The headline result

**v5a found the defect that actually shipped. v2a did not — it acquitted the two branches that
carry it, and its acquittal reproduced the exact reasoning error that the original v3 made.**

This is the first target in the program with strong, independently checkable ground truth: the pull
request merged, hung production, was reverted six days later (`tokio-rs/tokio#8057`), and was
re-landed correctly four months after that (`#8337`). The defect is that `Spawner::spawn_task` has
three post-push branches and only the "spawn a new thread" branch received the shutdown recheck the
pull request's own second commit added; the other two call `notify_one()` with no recheck and no
drain, and `notify_one()` is inert once every worker has left `wait_for_task`.

| | v5a | v2a |
| --- | --- | --- |
| Ground-truth defect (branches B and C) | **found** — sole finding, P1 `must-fix`, verifier-confirmed | **acquitted** — examined explicitly, judged safe, never re-checked |
| What it published instead | — | a different stranding path: the `WouldBlock` arm at `pool.rs:437-443`, P2 `must-fix`, verifier-confirmed, not reported by any prior run |
| Fix quality | verifier **rejected** the narrow per-branch patch and corrected it to the invariant level | n/a |
| Derived status | Changes Requested (advisory) | Changes Requested (advisory) |

Both runs land on the same status, which is why status alone is a poor discriminator: v2a is right
for the wrong reason.

**v2a's acquittal, quoted:** "any worker whose counters still make it look 'available' has
necessarily not yet run its own post-loop drain, and the shard `Mutex`'s lock/unlock ordering
guarantees that drain will observe an already-completed push (I traced this through explicitly and
it holds up)." The premise fails because `dec_num_idle_threads()` happens *before* the worker's
final drain sweep and `dec_num_threads()` *after* it — so a worker whose counters still look
available can already have drained. That is the whole bug.

**This is a regression against v2a's own ancestor.** On this same target the original v2 implicated
both unguarded branches at P1, as did v4 and v5. Only v3 got it wrong, and v3's error was the same
shape: it called the "at max threads" branch "self-healing via the busy-loop's full-shard rescan
since `idle == 0` implies no thread is parked in `wait_for_task` there."

## The most important mechanism result: N2 changed the fix

The dispatch flagged v5a's fix-sufficiency check (N2) as the single most important thing to observe
here, because the ground truth is a bug class where a narrow one-branch repair is exactly the wrong
answer — that is the mistake the pull request itself made.

v5a's primary drafted precisely that wrong fix: copy branch A's recheck into B and C. **Its verifier
refused it**, named the broken invariant, gave a coverage verdict for each of the three sibling
paths, and corrected the fix to close the race once, centrally, in `ShardedQueue::push` or
`BlockingPool::shutdown` under the same lock that flips the shutdown flag. The primary adopted the
correction, moving the published `fix` coordinate from `pool.rs:453` to `sharded_queue.rs:170`.

That is the shape of the real-world corrected re-land rather than the shape of the repair that
failed. **This is the first run in the program where the fix-sufficiency check changed the substance
of a published fix**, and it happened on the one target where getting it wrong had a documented
production consequence.

## Why neither architecture's verifier caught v2a's acquittal

Structural, and the most transferable finding of this round: **an acquittal is not a candidate, and
verification only sees candidates.**

- v2a's verifier received only the surviving candidates. The Code finder's acquittal of branches B
  and C was checked by nobody.
- v5a's clean-verdict verifier (G3) *does* attack a whole disposition ledger — but it only fires at
  **zero** survivors. v2a had one survivor, so an equivalent mechanism in v2a would not have fired
  either.

A false acquittal sitting beside a true candidate is currently invisible to both designs. v2a's own
report says so plainly rather than letting its confirmed finding stand in for the miss, which is the
disposition-ledger discipline doing exactly what it was added for — the error is recorded in the
artifact even though no mechanism caught it.

## Mirror truncation — the fix for the original round's disclosed contamination

The original test-3 README discloses a methodology failure: its mirror was **not** truncated, and v4
found the post-merge revert commit via an incidental `git log --all`, citing the revert's own message
as "decisive history evidence." That made v4's confidence unavailable to a contemporaneous reviewer.

This round closes it. A staging mirror was fetched (`master` plus `refs/pull/7757/head`), then a
fresh bare mirror was built by pushing **only** the two pinned SHAs into it, so object transfer
stopped at the head:

```
$ git -C /tmp/handoff3/mirror-tokio log --all --oneline | head -3
9de7950e rt: fix sharded blocking pool deadlock and lost wakeups
11cf7b5d rt: improve spawn_blocking scalability with sharded queue
43134f1e wasm: add wasm32-wasip2 networking support (#7933)

$ git cat-file -e 56aaa43e      # the revert, tokio-rs/tokio#8057
fatal: Not a valid object name 56aaa43e
$ git cat-file -e 8b13642a      # the corrected re-land, #8337
fatal: Not a valid object name 8b13642a
```

Both negative checks were repeated inside each run clone. The newest reachable commit in either
clone is the pinned head. **Every agent in both runs independently reported reading no history
beyond the pinned head**, and their quoted command lists bear that out — the only history commands
were `git log --oneline -3/-5` on the pinned branches and `git show master:<path>` reads.

## Regression watch

- **v2a / ground-truth miss via false acquittal — the most serious result in the re-test series so
  far.** The patched Panel line missed a defect its own unpatched ancestor found, by acquitting the
  right code with wrong reasoning. Neither fix under test (`326ef6f`, `940aa2c`) targets this failure
  mode; both are about doc-sync drift sweeps, and both worked correctly here (a clean negative). The
  miss is in concurrency tracing, not in the mechanisms this round was built to check. n=1, and the
  natural next step is replicates on this target's Code axis to see whether the acquittal is
  systematic or sampling.
- **A verification hole both architectures share.** Acquittals are unverified by construction:
  v2a's verifier sees only candidates, and v5a's ledger-attacking verifier fires only at zero
  survivors. On this target that hole is exactly where the ground truth sat. Worth considering
  whether the clean-verdict trigger should extend to "any run whose ledger contains an acquittal on
  the same bug class as a surviving candidate."
- **v5a / N2 fix-sufficiency: fired and materially improved the output.** First time in the program.
  Recorded as the mechanism's strongest evidence to date.
- **v5a / G1 question channel: fired**, on the adaptive-shard-count claim — the prediction in the
  handoff's checklist, met exactly.
- **v5a / N4 `plausible`: still never fired**, now across all three targets. DESIGN.md's note that
  the branch is untested stands, and after three targets it is fair to ask whether it is reachable
  at all.
- **v2a / C4 question routing: fired by rule**, on the residual-mutex contention claim — the
  improvised behavior from the original round is now contractual.
- **v2a / verifier caught a fabricated quotation.** The Requirements finder's scope-creep candidate
  quoted issue text that does not exist; the verifier checked the quotation against the real issue
  and refuted on that basis. First recorded instance in the program, and a direct vindication of the
  claim/support split.
- **Packet hygiene note.** v2a's verifier found and read a staging file this session had left in
  `/tmp/handoff3/` while building the packet. The outcome was correct and no network or mutation was
  involved, but future packets should stage such files outside the paths a sub-agent may browse.
