## The headline result

**Both prototypes found a real, previously unreported defect in a pull request the original round
called clean.** The 2026-09-01 comparison produced zero findings from all four prototypes, and the
target carries a human `APPROVED` review plus a detailed technical LGTM; the test-2 evaluation
treated it as the clean target whose only point of interest was the sub-threshold `redis.conf`
scope item.

v2a's F1 and v5a's sole finding are the same defect, reached independently in separate clones with
no shared state: `updateShardId()` keys its replica-propagation branch on `slaveof == NULL` rather
than the master flag, so a demoted master whose new master is not yet known pushes its new shard id
onto its attached replicas; `myself->shard_id` becomes the new shard before `myself` is re-pointed,
and the PR's own new guard at `src/cluster_legacy.c:5428` computes `shard_changed == 0` when the
sub-replica safeguard later flattens the node. The cached master survives and `repl_down_since` is
not reset — the failover-eligibility window the pull request exists to close, on the sub-replica
path its body claims to cover.

Three fresh-context verifiers (v2a's, and both of v5a's) independently reconstructed the mechanism
from the code. The convergence is the strongest signal in this round; it is also, per the dev-set
caveat above, not holdout evidence — both skills were designed by authors who had seen this
target's earlier results, though neither skill nor either author had seen this defect, which no
prior run reported.

**They disagree on the merge consequence, and that is the second result.** Same priority (P2), same
confirmed mechanism, opposite action and status: v5a `must-fix` → `Changes Requested (advisory)`;
v2a `consider` → `Approved (advisory)`. Neither is obviously wrong under its own contract — v5a's
rubric licenses `must-fix` from a demonstrated data-loss consequence on an authoritative path;
v2a's verifier weighed the same mechanism against a trigger needing a node-join race plus the new
master failing before first sync, and kept `consider`. A calibration question for the program, not
a defect in either run.

## Regression watch

- **v5a / clean-verdict verifier (G3): fired and justified its cost, but through the aside channel.**
  It upheld all 18 dispositions and re-opened none, so by the letter of the mechanism it found
  nothing; its one permitted observation aside is what exposed the hole in the primary's own row-1
  acquittal. Worth watching whether that is the normal shape — if asides rather than re-openings are
  where the value lands, the mechanism's contract may be describing the wrong output.
- **v5a / follow-up round (N3): load-bearing.** The late candidate reached render eligibility after
  the first batch was dispatched; under the pre-N3 rule it would have been dropped on batch timing
  or published unverified. This is the first run in the program where N3 changed the outcome.
- **v5a / `plausible` (N4): still never fired**, across both targets run so far. DESIGN.md's own note
  that the branch is untested still stands.
- **v2a / no-issue rule (C2): worked as written.** The Requirements finder built a 16-row body-claims
  ledger from the PR body's claims and non-goals, tested the non-goals as scope boundaries, inferred
  nothing from the diff, and disclosed "issue alignment unavailable". Two items landed in the
  "cannot tell from the code" bucket and correctly bypassed the verifier as questions.
- **v2a / C9 changed-contract sweep on a target with no known drift: correct negative.** Three
  contracts written down with paired searches, every live peer dispositioned, no stale peer found —
  and the Code axis's sync-drift section reached the same conclusion. A clean result here is the
  right outcome, not a miss.
- **v2a / Code axis returned zero candidates** while the Requirements axis returned both findings.
  Combined with target 1 (where the Code axis missed the validator regex the Requirements axis
  found), the Code axis is now the weaker arm on both targets run so far. Worth watching on target 3,
  whose known ground truth is a code-level concurrency regression with no requirements framing.
- **Status calibration across prototypes** is the open question this round raises: the same confirmed
  mechanism produced `Changes Requested` from one skill and `Approved` from the other. Target 3's
  known shipped regression will test the same axis with a much higher-stakes item.
- **Model mismatch, discovered after the round completed.** Both runs used `claude-fable-5-1`, not
  the Sonnet 5 tier the program intended, because the dispatches inherited the harness default
  instead of setting a model explicitly. The two prototypes remain matched to each other here, so
  the head-to-head result (both finding the same defect, disagreeing on severity) stands; what does
  not stand is any comparison of these columns against the original GLM round or against test 1's
  Sonnet-5 runs. Future dispatches pass the model explicitly.

  verified clean at `c54fa4184` throughout — but the cost columns are not usable and the runs did not
