## 2. Findings surviving to publication, in full

### Finding 1 — `hyper/dispatch/ready-stream-ci-gap`

- **Priority / action:** P2 / consider (`blocking=false`)
- **Kind:** `maintainability`
- **Anchor:** `Cargo.toml:243-246` (`RIGHT`, head) — the new `[[test]] name = "ready_stream" ... required-features = ["full", "tracing"]` block
- **Fix location:** `.github/workflows/CI.yml:69` (the `test` job's `include:` matrix)
- **Claim:** The new `ready_stream` test target is not built or run by any CI job.
- **Trigger scenario:** Any CI job in `.github/workflows/CI.yml` runs `cargo test`; every job's `--features` argument omits `tracing`.
- **Impact:** `Cargo.toml:246` gates the test behind `required-features = ["full", "tracing"]`. `src/trace.rs:5` hard-fails the whole crate build (`compile_error!`) if `feature = "tracing"` is enabled without `RUSTFLAGS='--cfg hyper_unstable_tracing'`. No job in `.github/workflows/CI.yml` sets both `tracing` and that `RUSTFLAGS` for a `cargo test`/`cargo build --tests` invocation (the one job that does set the RUSTFLAGS+feature pair, `features`, runs `cargo hack --no-dev-deps check ...`, which is a `check`, not a `test`, and `--no-dev-deps` additionally strips dev-dependencies before checking, and `cargo check` does not build `tests/` targets regardless). The regression test that the PR author wrote specifically to reproduce the reported production stall therefore never executes automatically; it only runs via the exact manual command given in the PR body.
- **Change requested:** Add a `test`-job matrix leg (or a new job) that runs `cargo test --features full,tracing` with `RUSTFLAGS: "--cfg hyper_unstable_tracing"` set.
- **Verification status:** Not independently verified — not required. This is a hygiene/test-infrastructure candidate; the rubric routes every such candidate to `kind=maintainability` / `action=consider` categorically ("a hygiene candidate is maintainability for routing and consider for action, so it never qualifies for mandatory verification on its own" — `review-rubric.md` §Complete inspection), and it does not independently fall into any of the other mandatory-verification categories (security/authorization, data loss/corruption, destructive migration, externally observable compatibility break).
- **Evidence (decisive citations):** `Cargo.toml:243-246` (new test entry, diff); `src/trace.rs:1-11` (the `compile_error!` gate, unchanged, read as bounded range); `.github/workflows/CI.yml` — read in full (340 lines; justified below in §5 as a risk-led-discovery whole-file read for the "test hygiene" risk signal) — specifically the `test` job matrix (lines 54-96), the `features` job (lines 149-173), and confirmation no other job runs `cargo test`/`cargo build --tests` with `tracing` enabled.

### Finding 2 — `hyper/tests/ready-stream-missing-assertions`

- **Priority / action:** P3 / consider (`blocking=false`)
- **Kind:** `maintainability`
- **Anchor:** `tests/ready_stream.rs:242-244` (`RIGHT`, head) — the `while let Some(chunk) = client_stream.recv().await { bytes_received += chunk.len(); }` loop
- **Fix location:** `tests/ready_stream.rs:244` (immediately after the loop closes)
- **Claim:** `body_test` never asserts the received byte count or response status; it only observes whether the connection hangs.
- **Trigger scenario:** `cargo test --test ready_stream --features full,tracing` runs to completion without hanging.
- **Impact:** The only "check" the test performs is implicit: it hangs if the exact reported deadlock recurs. It never calls `assert_eq!` (or any assertion) comparing `bytes_received` against the expected `TOTAL_CHUNKS * CHUNK_SIZE` (16 × 65536 = 1,048,576 bytes), and never inspects the response status. Traced the termination condition: `client_stream.recv()` returns `None` when its `mpsc::UnboundedSender` (`server_stream.write_tx`, held inside the `TxReadyStream` moved into `http_builder.serve_connection`) is dropped — which happens whenever `server_task`'s `conn.await` future completes, for *any* reason, including a hypothetical future regression that makes the connection finish early (e.g. `Dispatcher::is_done()` returning true prematurely) after writing only part of the body. In that scenario the client's `while let` loop would exit normally (no panic, no hang) with `bytes_received` short of the expected total, and `body_test` would still report success.
- **Change requested:** Add `assert_eq!(bytes_received, TOTAL_CHUNKS * CHUNK_SIZE)` (and a response-status check) directly after the receive loop.
- **Verification status:** Not independently verified — not required, same categorical hygiene/`consider` routing as Finding 1.
- **Evidence (decisive citations):** `tests/ready_stream.rs:241-249` (the full `body_test` tail — receive loop, cleanup, closing brace; read as part of the fully-shown new file, no re-read needed per rubric's "a file the diff adds is already fully present in it" rule); `tests/ready_stream.rs:32-78` (`TxReadyStream::new_pair`/`send`/`recv`, to trace which sender's drop closes the channel).
