Both prototypes on Fable independently found — and three independent fresh-context verifiers
confirmed — a real defect in a change that four earlier prototypes, a maintainer's `APPROVED`
review, and a detailed technical LGTM had all called clean. Both prototypes on Sonnet 5 missed it,
and each did so by reaching the correct hypothesis and then acquitting it on the same specific
error.

**The shared error.** `updateShardId()` propagates a shard id to a node's slaves only when
`node->slaveof == NULL`. Both Sonnet runs reasoned that the demotion handler always sets
`sender->slaveof` before calling it, so the propagation branch never runs. That holds only when
`hdr->slaveof` resolves to a node this peer already knows. When it does not — the exact case the
sub-replica safeguard exists to handle — `sender->slaveof` stays `NULL`, the propagation branch
runs, and `myself->shard_id` is rewritten before `clusterSetMaster` computes `shard_changed`.

- **v2a (Sonnet)**, Requirements finder, ledger row: "`src/cluster_legacy.c:3221-3234` updates
  `sender`, not `myself` | acquitted". Both finders returned zero candidates, so **the verifier was
  skipped by rule** and nothing checked it.
- **v5a (Sonnet)** raised it as a formal candidate and refuted it, calling the conclusion
  established "structurally — not probabilistically". Its **clean-verdict verifier fired, examined
  that very disposition, and strengthened the refutation.**

That second case is the more troubling one: the mechanism designed to attack acquittals ran, looked
directly at the right row, and agreed with the error.

## What this does and does not license

It does **not** license "Fable is better than Sonnet at code review." Two runs per cell, one target,
one diff. On target 3 — the target with externally verified ground truth — Sonnet 5 v5a found the
shipped defect and its verifier corrected the fix to the invariant level, while Sonnet 5 v2a missed
it. Model behavior here is target- and run-dependent, not a ranking.

What it does license is narrower and more useful:

1. **The Fable findings stand on their own evidence.** Three fresh-context verifiers reconstructed
   the mechanism from code. A later run failing to find it does not retract it; it is a recall
   difference, not a refutation. The Fable data is retained in full for exactly this reason.
2. **A single run is weak evidence of absence.** The same skill, same packet, same clone, different
   model produced 2 findings and 0 findings. Any conclusion of the form "prototype X finds nothing
   on target Y" needs replicates before it means anything.
3. **The verification hole is now observed three times.** Target 3 (v2a), and both prototypes here.
   An acquittal is checked only if a candidate survives to trigger verification — and even when
   v5a's ledger-attacking verifier did run, it confirmed the error rather than catching it.

## Deviations and disclosures

- **Session-relayed notifications.** A paused primary does not receive its own children's
  completion notices, so the session relayed them. v2a's orchestrator treated that relay as
  untrusted, independently verified every claim in it against the finder reports and the code, and
  documented doing so. In both cases the finders had already returned before any relay was sent, so
  no relay could have shaped review findings — only which disclosures the final reports make. The
  session did ask each orchestrator to state specific things plainly (an acquittal quoted in full;
  whether the `redis.conf` item appeared anywhere). Recorded here so the record shows it.
- **Prior third-party review state was withheld from v2a's finders** in both the Fable and Sonnet
  runs — verified by grepping the Fable run's saved shared block — so it is not a difference between
  them.
- **Digest determinism across models.** v5a's context digest is byte-identical between the Fable and
  Sonnet runs (`cce534b0751db6cad37be654fee7d885079464e1d486b83efb6f935a324a661f`), each computed
  multiple independent ways. F1 holds across a model change.
