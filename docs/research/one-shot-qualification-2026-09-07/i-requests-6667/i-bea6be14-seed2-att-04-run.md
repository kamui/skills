## 2. Findings for publication (full)

### [P0] [must-fix] Shared default SSLContext lets a client certificate leak into unrelated requests

- **Priority / action:** P0 / must-fix / blocking=true / `kind=invariant`.
- **Anchor:** `src/requests/adapters.py:94-95` (`elif verify is True: pool_kwargs["ssl_context"] = _preloaded_ssl_context`), `side=RIGHT`.
- **Fix location:** `src/requests/adapters.py:94-109` (widened from my original `:102`-only draft after the verifier's concurrency bug-class check found the single-line fix location insufficient — see §4; this final range spans both the shared-context assignment at :94-95 and the `client_cert` routing at :102-109 that the fix must coordinate).
- **Claim (rule level, per `verifier-concurrency.md` widening):** the per-request TLS `ssl_context` handed to urllib3 for a `verify=True` connection must never be a context that a *different* logical request can also mutate or whose loaded identity a different logical request can inherit; `_urllib3_request_context()` breaks this by handing every `verify=True` request — regardless of whether it supplies a client certificate — the exact same module-level singleton `_preloaded_ssl_context` (`src/requests/adapters.py:75`), and urllib3's `ssl_wrap_socket()` (`urllib3/util/ssl_.py:427`, installed version 2.7.0) unconditionally calls `context.load_cert_chain(certfile, keyfile)` on whatever `ssl_context` it is given whenever a `certfile` is present.
- **Trigger:** any single request made with the default `verify=True` and a client certificate (`session.get(url, cert=(certfile, keyfile))`), followed by **any other** `verify=True` request in the same process — even sequentially, single-threaded, to a completely unrelated host, with no `cert=` argument at all.
- **Impact:** the first client-cert request permanently loads that certificate/private key into the shared, process-wide `_preloaded_ssl_context` object. Every subsequent `verify=True` request in the process — to any host, without specifying a client cert — silently reuses that mutated context and can present the leaked client identity during its TLS handshake, because both requests are pool-configured with the identical `ssl_context` object reference (confirmed by direct object-identity check, §5). This also compounds into a genuine concurrent-mutation hazard: urllib3's `_ssl_wrap_socket_and_match_hostname()` (`urllib3/connection.py:935-937`) additionally writes `context.verify_mode` and `ssl_wrap_socket()` calls `context.set_alpn_protocols(...)` on this same shared object on **every** `verify=True` connect, from any thread, unsynchronized — exactly the "reconfiguring it once it is used" hazard flagged (for a different sub-case) in the PR's own review thread (`tiran`, non-review comment #5: *"Adding new certs to the internal trust store is fine, but changing ciphers, verification settings, or mTLS certs can lead to surprising behavior."*). At the merge-base, `_urllib3_request_context()` never populated `pool_kwargs["ssl_context"]` for `verify=True` at all, so urllib3 built a fresh, connection-private `SSLContext` per connection (`git show 8dd3b26b:src/requests/adapters.py:75-102`); the diff removed that per-connection-privacy guarantee that the unchanged `load_cert_chain()`/`verify_mode=`/`set_alpn_protocols()` calls in urllib3 relied on, so introduced-here gate 2 is satisfied via "removed a guarantee unchanged code relied on."
- **Change (final, published text, as widened by the verifier's concurrency bug-class check — see §4):** In `_urllib3_request_context()`, at both the direct-pool and proxy call sites that consume the same `pool_kwargs`, stop treating `_preloaded_ssl_context` as the default whenever a client certificate is involved: key any preloaded context on the exact `client_cert` value, or build a fresh context per distinct `client_cert`, falling back to the shared cert-free singleton only when `client_cert is None`. Locking or re-serializing access does not fix this: the shared object's identity is the defect, and it leaks even under fully serialized, single-threaded access. (My own first draft, before verification, proposed only "never route a `client_cert` request through the shared singleton"; the verifier showed this closed just one interleaving and one call site, so I widened it before publishing, per §4's "What I did with this return.")
- **Verification status:** `independent-confirmed`. See the verbatim verifier exchange in §4.

  - `git show 8dd3b26bf59808de24fd654699f592abf6de581e:src/requests/adapters.py:75-102` (merge-base) — no `ssl_context` key ever set, establishing introduced-here.

> ### Concurrency/invariant bug-class check (per `verifier-concurrency.md`)
>
> 1. **Invariant at rule level:** The SSLContext object used to perform a TLS handshake for connection C must never carry client-certificate/private-key material (loaded via `load_cert_chain`) other than what the specific request establishing C supplied via its own `cert=` argument — i.e., *client-certificate identity loaded into an SSL context object must never be observed inconsistent with the `client_cert` of the request currently using that object.* At the merge-base this held because urllib3 built a fresh, pool-private `SSLContext` per `HTTPSConnectionPool` (no `ssl_context` kwarg was ever passed), so `load_cert_chain()` only ever mutated a context scoped to pools sharing identical `cert_file`/`key_file`.
>
> 2. **Shutdown question: No.** This is a pure steady-state defect; it requires no runtime shutdown, teardown, or error path. Steady-state trace, `FAILS`:
>    - `src/requests/adapters.py:95` hands out the literal singleton for every `verify=True` call.
>    - `src/requests/adapters.py:102-109` attaches `cert_file`/`key_file` to that same `pool_kwargs` when `client_cert` is set.
>    - `urllib3/util/ssl_.py` `ssl_wrap_socket()`: `context.load_cert_chain(certfile, keyfile)` mutates the exact singleton object on first connect.
>    - Any later `verify=True` connection (new host, pool expiry, pool exhaustion, a distinct `Session`/`HTTPAdapter` in the same process) receives the identical, now-mutated singleton via `urllib3/poolmanager.py`'s shallow-copy passthrough, and its handshake presents the leaked identity — with zero errors, zero exceptions, and no ordering requirement beyond "the cert-bearing request connects before the innocent one."
>
> 3. **Sibling interleavings** (concurrent actors touching `_preloaded_ssl_context` / `pool_kwargs["ssl_context"]`):
>    - **Sequential, cert-request then plain request (different hosts):** deterministic leak, not a race — demonstrated directly by the evidence script. FAILS.
>    - **Concurrent, cert-request vs. plain request (overlapping in time, different hosts):** in addition to the leak, this races an in-flight `SSL_CTX_load_cert_chain()`/`SSL_CTX` reconfiguration against a concurrent handshake using the same C-level `SSL_CTX` object — precisely the hazard tiran named ("It is thread safe as long as you don't reconfigure it once it is used by a connection... mTLS certs can lead to surprising behavior"), which the review record raised only for *external* tampering, never for this internal reconfiguration path. Strictly worse than the sequential case (adds a thread-safety/UB hazard on top of the leak). FAILS.
>    - **Two concurrent cert-bearing requests with *different* client certs (cert1 vs. cert2, different hosts):** both call `load_cert_chain()` on the same shared object; whichever call lands last "wins," and every connection thereafter (including cert1's and cert2's own later connections) presents whichever identity loaded last — a cert-confusion hazard between two legitimate mTLS users, not just a cert-vs-no-cert leak. FAILS.
>    - **Independent `Session`/`HTTPAdapter` instances in the same process:** because `_preloaded_ssl_context` is a *module*-level singleton rather than per-adapter/per-session, isolation attempts at the Session level (e.g., "create a fresh Session per tenant/credential scope") do not isolate this state at all. FAILS.
>    - **Already-pooled, already-connected socket reuse:** does NOT trigger a new `load_cert_chain()` call (no fresh handshake), so an already-open keep-alive connection to an innocent host is not retroactively compromised — only *new* handshakes on the shared context are affected. This bounds but does not eliminate the bug, since new handshakes are routine (new hosts, pool exhaustion, idle-timeout reconnects).
>
