### C1 (concurrency) — full depth

**Premise:** Holding `ac.mu` across `go ac.resetTransportAndUnlock()` (clientconn.go:996) is unsafe because the spawned goroutine never calls `ac.mu.Lock()` itself before relying on the lock.

**Falsifying condition:** Go's `sync.Mutex` has no goroutine-affinity — lock state is a property of the mutex value, not of the calling goroutine, and the `go` statement establishes a happens-before edge from the spawning point into the new goroutine's start (Go memory model). Handing off a held lock to a new goroutine to release is therefore memory-safe by construction, provided exactly one Unlock eventually occurs.

**Trace of the opposite branch:** At `updateAddrs`, `ac.mu.Lock()` (clientconn.go:948) is held continuously through every intermediate branch (950,960,971 all `Unlock`+`return` before reaching 996); none of those paths reach line 996 without still holding the lock. Inside `resetTransportAndUnlock` (clientconn.go:1234-1239), the function unconditionally performs exactly one `Unlock` on every exit path (1237, 1262, and paths downstream that re-`Lock`/`Unlock` in matched pairs at 1266/1269, 1278, 1283/1285, 1293/1297, 1301/1303). No path leaves the mutex locked or double-unlocks.
