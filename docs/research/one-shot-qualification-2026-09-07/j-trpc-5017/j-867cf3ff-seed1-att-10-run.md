## 2. Findings that survive, in full

### Finding 1 — `server/overwrite-never-with-branch`

- **Priority / action:** P3 / consider (`blocking=false`).
- **Kind:** `maintainability`.
- **Anchor:** `packages/server/src/core/internals/utils.ts:25-29`, side `RIGHT`.
- **Fix location:** same as anchor (omitted from the trailer per the contract, since fix == anchor).
- **Claim:** The new non-object branch of `Overwrite<TType, TWith>` —
  ```ts
  : TType extends any
  ? TWith extends any
    ? // Same as above: just overwrite TType with TWith
      TWith
    : TType
  : never;
  ```
  — contains a `: TType` branch that TypeScript's distributive-conditional semantics make unreachable: because `TWith` is a bare reference to the generic's own type parameter, `TWith extends any ? TWith : TType` collapses the *entire* expression to `never` the instant `TWith` is exactly `never`, regardless of which textual branch is written. The `: TType` branch, and the sibling doc comment ("Otherwise it will overwrite the entire TType with TWith, unless TWith is never"), both describe a fallback-to-`TType` behavior that can never actually execute.
- **Verification status and evidence:** **Primary-confirmed by direct execution**, not independently verified (not required — see §1's trigger analysis). Decisive evidence:
  1. `git show 2abb2d5cd19740be37272dac6ad7fdd36244ae54:packages/server/src/core/internals/utils.ts` — the merge-base version of `Overwrite` has no `TType extends object` split at all; it goes straight to `TType extends any ? TWith extends any ? {...} : never : never`. `TWith=never` already collapsed the entire type to `never` for **every** `TType` at the merge-base — so this dead branch, and the misleading comment, are wholly new content introduced by this diff (satisfies rubric gate 2, introduced-here, trivially, since the text is new).
  2. I wrote an isolated scratch file (`/tmp/qual137/work/j-867cf3ff-seed1-att-10/tstest/overwrite.ts`) containing the head version of `Overwrite` verbatim (copy, not an import — the clone was never touched) plus a type-level `Equal`/`Expect` harness, and ran `tsc --noEmit --strict` on it with the clone's own `packages/tests/node_modules/.bin/tsc` binary (permitted focused type-checking, offline, no network). `Expect<Equal<Overwrite<string, never>, string>>` **failed** to satisfy `true` (`tsc` reported `Type 'false' does not satisfy the constraint 'true'` at that line), and a follow-up `Expect<Equal<Overwrite<string, never>, never>>` **passed** with zero errors — conclusively establishing that `Overwrite<string, never>` is `never`, not `string`, contradicting the `: TType` branch's evident intent.
  3. `grep`-confirmed real call sites where `TWith` could plausibly be `never` for a non-object `TType`: `packages/server/src/core/internals/procedureBuilder.ts:41,44` compute `Overwrite<TPrev['_input_in'], TNext['_input_in']>` (and `_input_out` likewise) whenever a procedure's next builder step sets an input schema; a schema such as `z.never()` would instantiate `TNext['_input_in']` as `never`.
  4. I also proved this is **not a behavior regression**: `OverwriteOld<string, never>` (the merge-base implementation, tested in the same scratch file) also resolves to `never` — the externally observable result for this edge case is unchanged by the PR. This is a pure dead-code / comment-accuracy defect in newly written code, not a functional regression, which is why I priced it P3/consider rather than higher.
- **Trigger scenario:** A procedure chain reaches `Overwrite` with a non-object `TPrev[...]`/`TNext[...]` pair where the `TWith` side is exactly `never` (e.g., an input schema such as `z.never()` used after or alongside another schema). The type silently collapses to `never` instead of preserving the previous type, exactly as before this PR, but the new code and its comment now claim otherwise — a future maintainer reading this code and trusting the comment/branch would be misled about actual behavior.
